# 기록·결재 명세

설계변경(ECN) 판단을 바뀌지 않는 기록으로 남겨 결재·감사하는 규칙(기록·결재 편)과, 연락할 상대마다 만드는 알림 초안·공식 메일·통보 기록(통보 편)을 적는다.
코드 주석은 `docs/records.md`(통보) 4절처럼 편 이름과 절 번호로 가리킨다.

## 기록·결재

분석 결과를 ECN마다 **바뀌지 않는 기록(개정)**으로 남기고, 검토 요청 → 승인·반려·보류 → 실행 → 종료를 계정 단위로 처리하며, 모든 상태 변화를 **덧붙이기만 하는 해시 사슬 감사 로그**로 남긴다.

- 코드: 순수 계산 `ripple/records/`(상태 기계 `flow.py`, 감사 사슬 `chain.py`, 결재선·무비용·결재 소요 `approval.py`) · 저장소 `ripple/store/records/` · 서비스 `ripple/api/records.py` · 경로 `ripple/api/routes/records.py` · 계약 `ripple/contracts/records.py`. 화면은 `DESIGN.md` 13절.
- 잘못 계산하거나 잘못 판단한 채 승인되면 실제 비용 손실로 이어진다. 그래서 서버는 **화면이 보낸 숫자를 저장하지 않고 같은 요청을 다시 계산**한다.
- 승인은 **그 개정을 계산한 지도가 커밋 시점의 지도와 같고, 그 개정의 계산 판이 지금 판과 같을 때만** 받는다.

### 1. 범위

- 들어간 것: 기록 저장(개정), 검토 요청·취소, 승인·반려·보류, 실행 시작·종료, 감사 로그와 관리자 감사 확인, 실데이터 기록의 보기 범위.
- 정한 규칙
  - 승인·반려·보류는 **결재선의 지금 단계 결재자만**(추가 비용 건 = 파트장 → 팀장 → 본부장, 팀장은 파트장·본부장 단계를 전결 — 14절). 담당자는 기록·검토 요청·무비용 담당자 처리·실행·종료.
  - **자기 결정 금지**: 그 검토를 요청한 계정은 그 검토를 승인·반려·보류할 수 없다(로그인을 끈 개발 모드만 예외 — 감사 줄에 표시).
  - 확인 필요 항목이 남은 기록의 승인: 항목마다 '확인했음' 체크 + 사유. 승인 감사 줄에 체크한 항목 키를 남긴다.
  - 승인 뒤 활성 지도가 바뀌어도 **실행 시작은 허용**하고, 화면 안내와 감사 줄 세부(`other_map`)에 '다른 지도 기준'을 남긴다.
  - 개발 모드(로그인 끔)에서 한 승인은 업무 승인이 아니다. 로그인 모드에서는 그 승인으로 실행할 수 없고 **다시 검토·승인**받아야 한다.
  - **계산 판이 바뀐 진행 중 결재**: 배포로 계약·규칙표·파라미터·엔진 판이 바뀌면 그 전 개정은 다시 계산해도 같은 분석이 나오지 않는다.
    - 기록은 저장된 그대로(리포트) 보고 **반려·보류는 허용**, **승인·검토 요청은 지금 판으로 다시 기록한 개정만**(지도가 바뀐 개정과 같은 원칙).
    - 이전 판 개정에 한 반려·보류는 감사 줄 세부 `other_version`에 남긴다.
- 범위 밖: 승인 철회, 실적으로 비용 파라미터 자동 보정(실적 입력·예측 대비 표는 11절), 알림 발송, AI 비서 제안 작업의 승인 카드.

### 2. 기록과 개정

- **기록 본문**(`RecordBody`) = {ECN 번호, 지도 ID, **유효 데이터 모드**(지도 + 설정), 분석 결과 전체, 확인 목록}. 기록한 사람·시각은 본문에 넣지 않는다(개정 표에 따로).
- **기록 ID** = `R-` + SHA-256(본문의 정규 JSON) 앞 16자리.
  - 같은 내용이면 같은 ID, 데이터 모드만 달라도 다른 ID다.
  - 같은 ID인데 저장된 본문이 다르면 `integrity`(500)로 거절한다. 읽을 때마다(기록 조회·결정 때 확인 목록) 본문 해시를 다시 계산해 ID와 대조한다.
- **개정**: ECN마다 1부터 빠짐없이 오르는 번호. 개정 = (ECN, 번호) → 기록 ID · 기록 시각 · 기록한 계정(아이디·이름·역할·개발 모드) · 목록·이력용 요약(제목·변경 사유·판정·총액·마감일·기준일·확정일·보류·대안 여부·확인 항목 수).
- **문서로 넣은 요청**(1.27.0, `docs/input.md`(문서 접수)): 연산 여러 개 + 원문 정보(`ChangeRequest.source`: 원문 번호·개정·항목 수·뺀 수)를 그대로 기록·결재·리포트한다.
  - `source`는 분석 ID에 들어가지 않는다.
  - 같은 원문 번호의 설계변경을 이어 가면 그 ECN의 새 개정이 되고, 실행·종료된 ECN은 이어 가지 않는다.
  - 실데이터 모드의 `raw_text`는 확정한 항목 조각만이다.
- **같은 기록인가**(화면): 분석 ID는 계산을 바꾸는 입력만의 해시라 변경 사유·제목이 빠진다(변경 원인은 1.29.0부터 선주 요청일 때만 들어간다 — 허용 지연, `docs/domain.md` 14절. 의장품 선상 설치는 켰을 때만).
  - 화면은 분석 ID + 제목 + 변경 사유가 최신 개정과 같을 때만 '기록과 같음'으로 보고, 사유만 바꿔도 새 개정을 남길 수 있다(서버의 기록 ID는 본문 전체 해시라 원래 다르다).
- **확인 목록**(`ChecklistItem`) = 분석이 계산하지 못한 항목(`result.unresolved`) + 가져온 지도면 품질 리포트의 경고. 기록할 때 고정한다.
  - 키는 `analysis:<n>:<종류>`, `import:<n>:<코드>`(같은 결과면 같은 키).
  - 같은 종류(같은 이유의 미계산 · 같은 시트의 같은 경고)가 4개를 넘으면 한 항목으로 묶는다('발주 상태 10건: … — PO-0001, … 외 5건'). 사람이 하나씩 체크할 수 있는 크기로, 승인 요청의 체크 한도(1,000) 안에 들게 하려는 것이다.
- **저장 요청**(`POST /api/records`): {요청, 화면이 본 분석 ID, 저장 요청 ID(UUID), 기대 상태 버전(새 ECN이면 0)} + 작업 공간 토큰.
  1. 같은 저장 요청 ID를 이미 처리했으면 **다시 계산하기 전에** **처음 결과를 그대로** 돌려준다. 응답이 유실돼 다시 눌러도 개정이 두 번 생기지 않고, 계산 판이 바뀐 배포 뒤의 재시도도 같다. 그 ID를 다른 ECN·분석에 쓰면 `request_reused`(422).
  2. 요청이 시작될 때 잡은 작업 공간 세대로 **다시 분석**해 분석 ID가 화면이 본 것과 다르면 `analysis_changed`(409).
  3. 지도 전환 잠금 안에서(5절) 상태 버전을 대조(다르면 `ecn_changed` 409)하고, 기록·개정·상태·감사 줄·요청 결과를 **한 트랜잭션**으로 쓴다.
  4. 최신 개정과 같은 본문이면 새 개정 없이 그 개정을 돌려준다(`created = false`). 이때도 권한·잠김은 새 개정과 같이 본다(실행·종료 뒤에는 `locked`). 옛 개정과 같은 내용으로 되돌리는 것은 새 저장 요청일 때 새 개정이 되고, 그 개정은 옛 기록 ID를 가리킨다.

### 3. 상태 기계 (`ripple/records/flow.py`)

상태: 요청(기록 없음) · 분석 · 검토 · 승인 · 반려 · 보류 · 실행 · 종료. 상태가 바뀔 때마다 **상태 버전**이 1 오른다.

| 지금 | 행동 | 다음 | 누가 | 조건 |
|---|---|---|---|---|
| 요청·분석·검토·보류·반려·승인 | 기록 저장(새 개정) | 분석 | 기록 권한 | 실행·종료는 `locked`. 진행 중 검토는 '대체됨'으로 끝나고(감사 세부 `superseded_review_seq`), 옛 승인은 옛 개정에 남는다 |
| 분석 | 검토 요청 | 검토(1단계) | 기록 권한 | 그 개정의 지도 = 커밋 시점의 활성 지도, 계산 판 = 지금 판. 결재선을 이 검토에 고정(14절) |
| 승인(개발 모드 승인, 로그인 모드) | 검토 요청 | 검토 | 기록 권한 | 위와 같음 — 업무 계정으로 다시 승인받는 길(승인 표시는 지운다) |
| 검토 | 검토 취소 | 분석 | 요청한 사람 또는 팀장 | 보류 중에는 취소할 수 없다(전이표에 없음) — 결재자의 반려를 받거나 담당자가 새 개정을 기록해 검토를 끝낸다(대체됨) |
| 검토·보류(앞 단계) | 승인 | 검토(다음 단계) | 지금 단계 결재자 또는 팀장 전결 | 아래 승인과 같은 조건(단계마다). 검토 순번·요청자 그대로 |
| 검토·보류(마지막 단계) | 승인 | 승인 | 지금 단계 결재자 또는 팀장 전결 | 요청자 ≠ 결정자, 지도 같음, 계산 판 같음, 확인 목록이 있으면 전부 체크 + 사유 |
| 검토·보류 | 반려 | 반려 | 지금 단계 결재자 또는 팀장 전결 | 요청자 ≠ 결정자, 사유 필수. 어느 단계든 검토를 끝낸다. 이전 판 개정이면 허용하고 `other_version` 표시 |
| 검토 | 보류 | 보류 | 지금 단계 결재자 또는 팀장 전결 | 요청자 ≠ 결정자, 사유 필수. 같은 검토·같은 단계가 이어진다(순번·요청자 그대로). 이전 판 개정이면 `other_version` |
| 분석 | 담당자 처리(`settle`) | 승인 | 기록 권한 | **무비용 개정만**(14절, 아니면 `invalid_transition`). 지도·계산 판 같음, 확인 목록이 있으면 전부 체크 + 사유. 감사 세부 `no_cost` |
| 승인 | 실행 시작 | 실행 | 기록 권한 | 로그인 모드에서 승인이 개발 모드였으면 `dev_approval`. 지도가 다르면 허용하고 `other_map` 표시 |
| 실행 | 종료 | 종료 | 기록 권한 | |

그 밖의 조합은 `invalid_transition`(409). 결정·검토 취소 요청은 **화면이 본 진행 중 검토의 순번**(`review_seq`)을 함께 보내고 서버가 대조한다 — 취소 뒤 다시 요청한 검토에 첫 검토 화면의 늦은 승인이 붙지 않는다.

**검사 순서**(먼저 걸린 이유로 거절):

1. 기대값(상태 버전·개정·기록 ID·검토 순번, 다르면 `ecn_changed`)
2. 전이표(무비용 담당자 처리는 무비용 개정만)
3. 권한·결재 단계·자기 결정(`forbidden` — 결재 권한이 있어도 지금 단계가 아니면 · `self_decision`)
4. 사유·확인 목록(`reason_required`·`checklist_required`, 승인 외 행동에 체크를 보내거나 확인 목록에 없는 체크를 보내면 거절)
5. 지도(검토 요청·승인, `map_changed`)
6. 계산 판(검토 요청·승인, `version_changed`)
7. 개발 모드 승인(`dev_approval`)

**계산 판** = 분석 ID에 들어가는 버전 묶음에서 지도를 뺀 것(계약·규칙표·파라미터·엔진, 대안 포함 분석이면 강도 규칙).

- 개정 본문의 판(`body.result.versions`)이 그 요청을 지금 분석할 때의 판(`ripple/engine/analyze.py` `analysis_versions`)과 다르면 '이전 판 개정'이다.
- 판 대조는 저장하지 않고, 행동할 때(저장소 트랜잭션 안에서 읽은 최신 개정 본문)와 상세를 읽을 때 계산한다(`ripple/api/records.py` `same_version_of`).

감사 줄 세부(`AuditDetail`): 앞·뒤 상태, 사유, 체크한 확인 목록 키(정렬), 결정이 묶인 검토 순번, 대체된 검토 순번, 다른 지도에서 실행(`other_map`), 이전 계산 판 개정의 반려·보류(`other_version`), 개발 모드 자기 결정(`self_decision`), 통보 기록(`notice`, 1.28.0), 결재선(형식 판 4, 14절 — 검토 요청의 결재선 `steps` · 결정한 단계 `step` · 팀장 전결 `proxy` · 무비용 담당자 처리 `no_cost`).

**통보 기록**(1.28.0, `action = notice`): 알림 초안마다 받는 쪽(알림 대상·받는 쪽 ID)에 **보냄 · 수령 확인 · 회신 받음**을 사람이 적은 날짜·메모와 함께 남긴다.

- 앱이 메일을 보내지 않으므로 '언제 알렸고 언제 확인받았나'를 당시에 남기는 장치다(공정위 사례에서 서면 지연발급은 전자서명일과 실적일 대조로만 밝힐 수 있었다).
- 상태·버전을 **바꾸지 않아** 결재 중인 다른 화면을 `ecn_changed`로 막지 않는다. 재생(`replay`)은 이 줄을 건너뛴다(앞·뒤 상태가 같고 `notice`가 있어야 함).
- 받는 조건: 기록 권한, 화면이 본 최신 개정의 기록 ID = 지금(아니면 `ecn_changed`), 날짜가 오늘(KST)보다 뒤가 아님(아니면 `invalid_transition` 422).
- 실행·종료 뒤에도 받는다(늦은 회신). 행동 API(`/actions`)로 보내면 거절한다.

### 4. 저장소와 감사 사슬

- 파일: `RIPPLE_DATA_DIR/records.sqlite3`(라이브는 Railway 볼륨 `/app/.data` — 지도·계정과 같은 곳, 깃 제외). WAL, `synchronous = FULL`, 외래 키 켬.
- **형식 판** = `PRAGMA user_version`(지금 4 — 판 2 → 3은 계약 1.28.0의 통보 기록 줄·변경 원인, 판 3 → 4는 결재선(14절: 진행 중 검토의 결재선·지금 단계, 감사 줄의 단계·전결·무비용, 담당자 처리 줄) 때문, 판 1 → 2와 같은 방식).
  - 판 3까지의 진행 중 검토(결재선 칸 없음)는 **팀장 한 단계(1/1단계)**로 읽는다 — 상태 행의 `ReviewInfo.steps·step` 기본값과 재생(`replay`)의 빈 결재선 = 팀장 한 단계가 같아 감사 확인(투영 = 재생)이 그대로 통과한다(`tests/checks/records_compat.py`).
  - 판이 없는데 표가 있거나, 모르는 판이거나, 파일이 손상됐으면 서버가 **시작을 멈춘다**(`RecordStoreError`) — 새 형식을 옛 코드가 조용히 고쳐 쓰지 않게.
  - 표 만들기와 판 적기는 한 트랜잭션이다.
  - 판 1 → 2(계약 1.18.0): 표는 같지만 판 1 코드가 읽지 못하는 내용(감사 줄 `other_version`, 기록 본문의 일정 위험)을 쓰기 시작하므로, 판 1 파일은 **시작 때 무엇을 쓰기 전에** 판만 2로 올린다(본문·감사 사슬은 그대로, 한 트랜잭션).
  - 판 1만 받는 옛 코드는 이 파일에서 시작을 멈춘다 — 옛 코드가 새 내용이 섞인 파일을 일부만 읽은 채 쓰기를 이어 가지 않게.
- 표: `records`(기록 ID → 본문) · `revisions`(ECN·개정 → 기록 ID·시각·계정·요약) · `ecns`(ECN → 상태 투영 `EcnStatus`) · `requests`(저장 요청 ID → 처음 결과) · `audit`(순번 → ECN·줄 내용·앞 해시·줄 해시, 덧붙이기만) · `meta`(사슬 머리: 마지막 순번·해시).
- 쓰기: 프로세스 잠금 + `BEGIN IMMEDIATE` 한 트랜잭션으로 기록·개정·투영·감사 줄·머리·요청 결과를 함께 쓰고, 하나라도 실패하면 모두 되돌린다.
- 읽기: 잠금 없이 **한 읽기 트랜잭션**(WAL 스냅숏)으로 — 상세에서 보기 범위(실데이터)를 판단한 뒤 다른 요청이 실데이터 개정을 커밋해도 같은 응답에 섞이지 않는다. 서버 한 대(복제본 없음)가 전제다.
- **감사 사슬**(`ripple/records/chain.py`): 줄 해시 = SHA-256(정규 JSON `{"prev": 앞 줄 해시, "entry": 줄 내용}`), 첫 줄의 앞 해시 = `0`×64. 줄 내용 = 순번·시각·계정·행동·ECN·개정·기록 ID·세부.
- **머리**: 끝 줄을 지운 것은 사슬만으로는 알 수 없어, 같은 트랜잭션에서 `meta`에 마지막 순번·해시를 적고 검증 때 대조한다. 덧붙일 때도 머리 순번이 마지막 줄과 다르면 `integrity`로 거절한다.
- **판 호환**: 표는 그대로(형식 판만 2)이고 저장되는 모델(개정 요약·상태·저장 응답)은 바꾸지 않는다.
  - 계약에 더하는 필드는 기본값이 있는 것만(감사 줄 `other_version = false`, 기록 본문의 일정 위험 `risk = null`).
  - 기본값이면 직렬화에서 빠지는 필드(사전 점검 `prechecks`, 1.34.0 중량 변화 `weight_change = null`, 1.35.0 비용 줄 구분 `kind`·`item`·`hours`와 구분별 합 `cost_split = null`)는 옛 본문을 다시 직렬화해도 글자가 같아 기록 ID(본문 해시)가 그대로다(`tests/checks/weight.py`·`tests/checks/cost_split.py` 옛 기록 호환).
  - 기록 ID·감사 해시는 저장된 문자열 그대로 계산하므로 옛 기록·감사 줄이 새 코드에서 그대로 읽히고 검증된다.
  - 계약 1.17.0 코드로 만든 저장소 고정 파일(`tests/compat/records_contract_1.17.0.sql`, 합성 지도)을 새 코드로 열어 검사한다(`tests/checks/records_compat.py`, 항목은 12절).
- **한계**: 파일 전체를 다시 쓰는 사람(모든 줄 해시와 머리를 다시 계산)은 막지 못한다. 변조를 **알아차리는** 장치이지 접근 통제가 아니다. 접근 통제는 볼륨 권한과 관리자 계정이 맡는다.

### 5. 지도 전환과 커밋

- 분석·대조·확인 목록 만들기는 잠금 밖에서 하고, **저장소 커밋만** 지도 전환과 같은 잠금(`Workspaces.pinned`, 내부 `_switch`) 안에서 한다. 잠금 안에서 요청이 잡은 세대가 아직 지금 세대인지 다시 보고, 다르면 `workspace_changed`(409)로 커밋하지 않는다.
- 커밋하는 동안 지도 전환은 기다린다(검사: 커밋 중 전환은 커밋이 끝난 뒤에 됨). 그래서 '승인한 순간의 활성 지도'가 감사 줄과 어긋나지 않는다.
- 검토 요청·승인의 지도 대조는 **그 개정의 지도 ID = 커밋 시점 활성 지도 ID**다. 지도를 바꿨으면 지금 지도로 다시 분석해 새 개정을 남긴 뒤 검토를 요청한다.

### 6. 감사 확인 (`GET /api/audit/verify`, 승인(결재자))

한 번에 아래를 모두 보고, 어긋난 것을 명사형 문장(`problems`)으로 돌려준다(`ok`, 줄 수, 기록 수, 처음 어긋난 순번, 머리 해시).

1. 사슬: 순번이 1부터 빠짐없이 이어지는지, 앞 해시 연결, 줄 해시 재계산, 머리(마지막 순번·해시).
2. 기록 본문: 모든 기록의 본문 해시 = 기록 ID, 색인 값(데이터 모드·지도 ID) = 본문.
3. 개정: ECN마다 개정 번호가 1부터 이어지는지, 저장한 요약 = 본문에서 다시 만든 요약.
4. 참조: 감사 줄의 (ECN·개정·기록 ID) = 개정 표, 감사 줄의 순번 = 내용의 순번, ECN 색인 = 내용.
5. 투영: 감사 줄을 처음부터 다시 돌린 상태(`replay`) = 저장된 상태(버전·개정·검토·승인 개정·개발 승인까지).
6. 투영 밖의 상태 칸: 실데이터 표시(개정 중 하나라도 실데이터면 참 — 체험 보기 범위를 정함)·제목·지도 = 기록 본문에서 다시 만든 값.
7. 개정마다 그 개정을 남긴 감사 줄(기록)이 있고 기록한 사람·시각이 그 줄과 같음(감사 줄 없이 끼워 넣은 개정 · 개정 표의 기록자·시각만 바꾼 것), 상세는 다른 ECN의 감사 줄이 섞이면 integrity.

화면: 관리자 사용자 메뉴 '감사 로그 확인…' → 정상이면 줄·기록 수와 머리 해시 앞부분, 어긋나면 처음 어긋난 순번과 이유 목록.

거절 이유(`detail = RecordProblem {code, message}`):

| code | 상태 | 뜻 |
|---|---|---|
| `ecn_changed` | 409 | 기대 버전·개정·기록·검토 순번이 지금과 다름 → 다시 불러오기 |
| `analysis_changed` | 409 | 다시 계산한 분석 ID가 화면과 다름 |
| `invalid_transition` | 409·422 | 지금 상태에서 할 수 없는 행동(422: 요청 모양이 틀림) |
| `locked` | 409 | 실행·종료 뒤 새 개정 |
| `map_changed` | 409 | 그 개정의 지도가 활성 지도와 다름(검토 요청·승인) |
| `version_changed` | 409 | 그 개정의 계산 판이 지금 판과 다름(검토 요청·승인) → 지금 판으로 다시 기록 |
| `dev_approval` | 409 | 개발 모드 승인으로 로그인 모드 실행 |
| `self_decision` | 403 | 내가 요청한 검토를 결정 |
| `forbidden` | 403 | 역할 밖(기록·검토 요청·담당자 처리·실행은 담당자, 결정은 지금 결재 단계의 결재자·팀장 전결, 검토 취소는 요청자·팀장) |
| `reason_required` · `checklist_required` | 422 | 사유 없음 · 확인 목록 미체크 |
| `request_reused` | 422 | 같은 저장 요청 ID를 다른 기록에 씀 |
| `not_found` | 404 | 기록이 없음(체험에게는 실데이터 기록도 없는 것처럼) |
| `integrity` | 500 | 저장된 본문 해시가 ID와 다름 · 사슬 머리가 맞지 않음 → 감사 확인 |

작업 공간 토큰이 지금 세대와 다르면 `workspace_changed`(409, 지도 전환 계약 그대로).

### 8. 권한과 보기 범위

- 권한 표(`ripple/contracts/auth.py`): `record` = 담당자, `approve` = 결재자(팀장(관리자) · 파트장 · 본부장, 계약 1.24.0 · 결재선 14절). 어느 단계를 결정하는지는 결재 규칙의 역할 → 단계(`ripple/records/approval.py`). 체험은 보기·내보내기만. 개발 모드는 모든 권한(모든 결재 단계).
  - 결재 행동 입구는 기록 또는 승인 권한이고, 행동마다의 권한은 상태 기계가 본다.
  - 로그인 모드의 관리자는 검토를 요청할 수 없으므로, 자기 결정 금지는 개발 모드·역할을 바꾼 계정의 방어선이다.
- 개발 모드(로그인 끔)의 기록·결정은 계정에 `dev = true`가 붙고, 이력 탭에 '개발 모드 기록'으로 보인다.
- **실데이터**: 실데이터 설정에서 남긴 기록이 하나라도 있는 ECN은 `real = true`(이후 개정에서도 풀리지 않음).
  - 체험에게는 목록에서 빠지고 상세·기록 조회가 404다. 기록 조회도 본문의 모드만이 아니라 그 ECN의 표시로 판단한다(실데이터 요청을 합성 지도에서 다시 저장한 개정도 숨김).
  - 기록 경로는 엔진 재계산만 하고 **외부 AI를 부르지 않는다**.

### 9. 화면 (`DESIGN.md` 13절)

- ECN 목록: 기록이 있는 줄에 상태 칩. 지금 지도 샘플에 없는 기록된 ECN은 목록 아래 '기록된 다른 설계변경'(누르면 그 기록의 요청을 지금 지도로 다시 분석).
- 결재자 목록의 거르기 칸 '결재 대기'(검토·보류 — 설계변경 목록이 없는 지도만 목록 위 묶음 '결재를 기다리는 설계변경', 마감일 급한 것부터): 누르면 그 개정의 **기록된 분석**(담당자가 기록한 조건 그대로)을 연다.
- 상세 결재 띠(머리 아래): 상태 칩 · 개정·기록한 사람·시각·검토 요청한 사람 · 알아야 할 한 줄 · 할 수 있는 행동.
  - 못 하는 행동은 흐린 단추와 이유 한 줄(같은 이유는 한 줄로), 역할 밖 행동은 아예 없다.
  - 같은 규칙을 `web/src/lib/records.ts`가 계산하고(vitest), 막는 것은 서버다. 띠는 화면의 분석과 결재 대상이 같은 ECN일 때만 그린다.
- **결정은 그 개정의 분석을 화면에서 볼 때만**: 승인·반려·보류는 계산이 끝났고 화면 = 그 개정일 때만 켜진다.
  - 지도나 계산 판이 바뀐 개정은 맞춰 볼 수 없어 반려·보류만 된다(승인·검토 요청은 흐린 단추 + 이유).
  - 화면이 그 개정과 다르면 '기록된 분석 열기'로 기록 조건을 지금 지도에서 다시 연다. 계산 판이 바뀐 개정은 다시 열어도 같은 분석이 나오지 않아 안내 한 줄과 '리포트 열기'로 저장된 기록 그대로를 보게 한다.
  - 실행 시작은 승인한 개정을 실행하므로 화면과 무관하다.
- 결정 대화상자: 승인은 확인 목록 체크 + 사유, 반려·보류는 사유.
  - 열 때의 대상(상태 판·개정·기록·검토 순번)과 확인 목록을 고정해 보낸다.
  - 그사이 새 개정·결정이 생겨 거절되면 대화상자를 닫고 띠에 '다시 불러왔으니 확인한 뒤' 안내(입력한 체크·사유가 새 개정에 붙지 않게).
- 다른 사람의 결재: 창이 다시 보이거나 초점을 받을 때와 보이는 동안 20초마다 목록을 다시 읽고, 고른 ECN의 상태 판이 바뀌었으면 상세를 다시 읽는다.
- 이력 탭: 감사 줄을 최신부터 — 누가·언제·무엇을, 개정이면 그 개정의 판정·총액·조건, 사유·확인 수·대체·다른 지도·이전 계산 판·개발 모드.
- 저장 요청 ID는 단추를 누를 때 만들고, 네트워크 실패(응답 없음)로 다시 누를 때만 같은 값을 다시 쓴다.
- **설계변경 검토서**(판단 리포트, `/app/report/<ECN>/<개정>`, DESIGN.md 14절): 기록된 개정 하나를 A4 세로 검토서로 보이고 위쪽 '검토서 인쇄'(브라우저 인쇄)로 PDF를 저장한다(서버에서 PDF를 만들지 않는다). 실제 야드 양식이 아닌 일반 사내 검토서 구성이다.
  - 결재란(담당 · 파트장 · 팀장 · 본부장)은 감사 줄 그대로다: 담당 = 그 개정의 마지막 검토 요청(무비용이면 담당자 처리), 단계 칸 = 그 검토의 단계별 마지막 결정(승인·반려·보류, 팀장 전결 표시, 단계 없는 판 3까지의 결정은 팀장 칸), 기록이 없으면 빈칸. 서명이 아니라 기록된 결재의 표시다.
  - 1.34.0부터 중량 변화 절(`docs/engine.md`(비용·일정) 12절)이 실리고, 그 전 기록은 '이 판 전 기록(계산 안 함)'으로 보인다.
  - 기록 ID는 개정마다 유일하지 않아(되돌린 개정은 옛 기록을 다시 가리킴) ECN 상세에서 그 개정의 기록 ID를 골라 본문을 읽고 ECN을 대조한다.
  - 결재 이력은 그 개정을 가리키는 감사 줄 + 뒤 개정의 기록이 끝낸 그 개정의 검토.

### 10. 운영

- 라이브: Railway `api` 서비스 볼륨(`/app/.data`)에 `records.sqlite3`(실적은 `outcomes.sqlite3`)가 생긴다. 재배포 때 짧은 중단(약 1분)이 있으니 발표·시연 중에는 배포하지 않는다.
- 되돌리기: 코드를 옛 판으로 되돌릴 때 기록 파일 형식 판이 더 높으면 시작을 멈춘다(계약 1.18.0(형식 판 2)처럼 첫 시작 때 판을 올린 뒤에는 이전 이미지로 API가 시작하지 않는다, 4절). 그래서 **배포 전에 볼륨 백업**을 만들고, 되돌릴 때는 그 백업으로 함께 되돌린다(계정 파일과 같은 정책, 그 사이에 남긴 기록은 백업에 없다).
- 계산 판이 바뀌는 배포(계약·규칙표·파라미터·엔진): 배포 전에 라이브에 진행 중 검토가 있는지 확인한다. 배포 뒤에는 반려·보류하거나 담당자가 지금 판으로 다시 기록해 검토를 다시 요청한다(1절).
- 감사 확인이 어긋나면 그 볼륨 파일을 그대로 보존하고(덮어쓰지 않음) 처음 어긋난 순번부터 원인을 찾는다.
- 시험 기록을 비울 때는 기록을 지우는 API를 두지 않고, 서버 시작 때 표지 변수(`RIPPLE_RESET_RECORDS`)로 기록·실적 파일을 보관 폴더로 통째로 옮긴다(새 감사 사슬로 시작, 옛 사슬은 보관 파일에 그대로 — `docs/operations.md`(배포) 4절).
- 시연 기록 시드를 켠 실시간 시연 배포(`RIPPLE_DEMO_SEED=on` + `RIPPLE_SYNTHETIC_CLOCK=live`)는 KST 날이 바뀌거나 시드 판이 바뀐 배포 뒤 기록·실적·수정 기록 파일을 같은 방식으로 자동 보관 폴더(`archive/records-auto-<KST 시각>`, 최근 14개)로 옮기고 그날 기준으로 새로 채운 파일로 바꿔 끼운다(새 감사 사슬, 옛 사슬은 보관 파일에 그대로 — `docs/operations.md`(서비스) 7절). 바꿔 끼우는 동안 기록 파일 연결은 열리지 않는다(`ripple/store/gate.py`). 시연에는 손으로 비우기가 필요 없다.

### 11. 결재·현황과 실적

- 결재자는 **결재선**(14절)이다: 추가 비용 건은 파트장 → 팀장 → 본부장이 차례로 승인하고(팀장은 파트장·본부장 단계를 전결), 무비용 건은 담당자가 처리한다. 자기가 요청한 검토는 어느 단계에서도 결정할 수 없다(3절).
  - 금액별 전결 규정(팀장 전결·부장 결재)은 없다(결재선은 금액과 무관). 옛 계정 파일의 결재 단계 칸은 읽을 때 버린다(`docs/operations.md`(서비스) 2절).
- **결재·현황**(`GET /api/manage/overview`, 화면 `/app/manage` — 결재자(팀장·파트장·본부장)가 로그인하면 먼저 보는 화면): 기록 저장소를 읽어 계산하고 저장하지 않는다.
  - 결재함: 검토·보류 중 개정 가운데 **보는 사람의 결재 단계 건만**(14절). 결정 기한 급한 순(→ 먼저 요청한 순). 결정은 '열기'로 업무 화면에서 그 개정의 기록된 분석을 보며 한다(9절 원칙 그대로). 줄마다:
    - 결정 기한 D-n
    - 미루면: 결정 기한 다음 날 확정 때 기준일보다 늘어나는 금액 = 기록된 추가손실 곡선 값. 기간 안 손실이 없으면 계산하지 않고 곡선 끝 날짜로 안내.
    - 더 저렴한 충족 대안과의 차액, 요청자·기다린 시간·확인 필요 수.
  - 현황: 결재 대기·결정 기한 임박(3일 이내·지남), 아직 결정 안 된 건수·금액 합, 실행 중, 기간 안 새 기록·종료, 상태별 건수, 블록별.
  - 성과(기간 7·30·90일·전체): 업무 결정 수(마지막 단계 승인 · 어느 단계든 반려·보류)·반려율·처리 시간 중앙값(기록 → 검토 요청, 결재 단계마다 그 단계가 시작된 때 → 결정, 단계별 중앙값 `steps`)·무비용 담당자 처리 수, 기한 안 결재 비율, 기한 안 결재로 피한 추가손실(그 승인들의 '미루면' 합, 계산된 건만), 더 저렴한 대안이 있던 승인, 담당자별 업무량(업무 분배용).
  - 날짜 기준은 기록마다: 실데이터 = KST 오늘·실제 결정 날짜, 합성 = 분석 기준일과 기록 뒤 지난 날수(합성 지도의 업무상 오늘은 지도 기준일이라).
  - 개발 모드 요청·결정은 성과·처리 시간·담당자별에서 뺀다.
- 담당자 목록의 거르기 칸 '내 건': 내가 최신 개정을 기록한 끝나지 않은 ECN(같은 건을 목록에 두 번 싣지 않게 따로 묶지 않음 — 10-30), 반려·보류는 줄 아래 사유 한 줄.
- 결재 중 조건 잠금(`web/src/lib/records.ts` `conditionLock`): 검토·보류·승인·실행 중인 건은 최신 개정을 기록한 사람만 상세 머리 조건(확정일·설계 승인·적용 시작일·변경 원인)을 바꾼다 — 결재자가 결재 중인 조건을 바꿔 다른 분석을 보지 않게. 종료된 건은 모두 잠근다.
- **실적**(예측 대비 실제, `ripple/store/outcomes.py` → `outcomes.sqlite3`)
  - 실행을 시작했거나 끝낸 ECN에 담당자가 실제 변경 비용과 구역 출구 지연(모르면 비움)·메모를 넣는다(결재 띠 아래 '실적 입력…', 금액은 만원 단위).
  - 기록·감사 사슬과 따로 덧붙이기만 하고, ECN마다 마지막 줄이 지금 값이다(고친 사람·시각이 남음).
  - 결재·현황 성과 아래 '예측 대비 실적': 승인한 개정의 총변경비용 대표값과 비교한 오차율, 예측 범위 안 여부, 출구 지연 예측 → 실적을 최근에 넣은 순으로 보이고, 오차 중앙값·범위 안 비율을 요약한다(기간과 무관하게 전부).
  - 쌓인 실적으로 비용 파라미터를 고치는 일은 범위 밖이다.

### 13. 결정 도우미 (계약 1.31.0, `ripple/brief/`)

팀장이 결재 띠에서 **30초 안에** 승인·반려·보류를 판단하게 돕는 카드다. 진행 중 검토(검토·보류) 개정의 **기록 본문**(그 개정을 기록할 때의 엔진 결과)에서 읽을 때 만들고 저장하지 않는다(기록 형식 그대로).

- **세 줄 요약**(줄마다 서버 템플릿, 명사형): 바뀌는 내용(change) → 안 정하면 무엇을 잃나(loss) → 권고와 근거(advice).
  - change: 변경 제목 · 영향 수 · 블록 · 총변경비용(범위).
  - loss: 마감일 상황 하나 — 마감일까지(D-n, 다음 날 늘어나는 금액) · 오늘 · 기간 안 손실 없음 · 이미 지남(오늘 확정할 때 기준일보다 늘어난 금액). 다음 날 금액은 결재함 '미루면'과 같은 계산(`records.metrics.delay_cost`, 곡선의 마감 다음 날 대표값)이고, 대표값이 0 이하면 결재함과 같은 분기(금액은 그대로 · 최대만 늘 수 있음 · 일정만).
  - D-n과 '이미 지남'은 업무상 오늘(`records.metrics.business_today` — 결재함과 같은 기준: 실데이터·실시간 시연 세계 = KST 오늘, 날짜에 멈춘 합성 = 분석 기준일)로 센다. 결정 대화상자는 기준일부터 센 D-n을 싣지 않는다(DESIGN.md 13절) — 결정 기한 큰 숫자 칸의 위험 색도 화면의 업무상 오늘부터 센다(`lib/revisions` `revisionGlance`, 도우미 결정 기한 카드와 같은 기준).
    - 날짜에 멈춘 합성 세계에서는 서버 문장의 D-n은 기록 기준일, 화면 결정 기한 카드는 지도 자료 기준일로 센다 — 실시간 세계(라이브)는 둘 다 KST 오늘이라 같다.
  - advice: **규칙 우선순위로 고정**(AI가 고르지 않음) — 더 저렴한 충족 대안(권고) → 보류 권고 → 선상 설치 → 판정(승인 가능 · 검토 필요/경고와 첫 이유). 같은 결과에서 상세 대안 탭의 권고와 어긋나는 권고가 나오지 않게.
  - 더 저렴한 대안의 차액은 **상세 대안 탭 권고 카드와 같은 공식**(요청안의 최적 총액 − 권고 총액, `web/src/lib/alternatives.ts`)이다. 결재함의 '더 저렴한 대안 차액'(`metrics.cheaper_by`, 요청안 확정일 총액 − 최저 비용 충족 대안 최적 총액)과 다른 이유: 도우미는 팀장이 바로 아래 대안 탭에서 보는 숫자와 같아야 하고, 결재함은 대안 탭 없이 줄만 보는 목록이라 요청 그대로의 총액과 비교한다. 기록 본문에 대안이 없으면 아래처럼 한다.
    - 지금 화면은 늘 대안 없이 기록한다: '검토 요청'·'기록만 남기기'는 화면이 보던 분석의 요청(`include_alternatives = false`)을 보내고, 대안 탭은 같은 요청을 대안 포함으로 따로 계산할 뿐 기록에 들어가지 않는다. 그래서 결재함의 '더 저렴한 대안 차액'(`cheaper_by`, 기록 본문의 대안을 기대)도 화면에서 만든 기록에는 나오지 않는다.
    - 기록할 때 대안 포함으로 바꾸지 않는 이유: 분석 ID가 화면의 분석과 달라져(대안 포함 여부·강도 규칙 판이 분석 ID에 들어감) 결정이 '화면 분석 = 기록' 대조(`lib/revisions` `sameAsRecorded`)에 막히고, 기록 본문에 대안을 따로 붙이면 기록 ID(본문 해시)와 옛 판 저장소 호환(`records_compat`)이 바뀐다.
    - 그래서 도우미가 **기록의 지도를 서버가 갖고 있고(`Workspaces.map_of`) 계산 판이 같을 때(`same_version_of`)만** 그 기록 요청을 대안 포함으로 한 번 계산한다(`ripple/api/brief.py` `recorded_alternatives`). 같은 지도·같은 판이면 결정적이라 상세 대안 탭과 같은 숫자이고, 계산 총액이 기록과 다르거나 조건이 안 맞으면 권고 후보에서 빼고 다음 우선순위(보류 → 선상 설치 → 판정)로 간다. 기록 저장 형식은 그대로이고, 계산은 도우미 기억에 없을 때만 한다(약 0.1~0.7초). 결재함의 대안 차액은 여전히 기록 본문의 대안만 본다.
- **서명 전 확인할 것**(최대 3개): 판단이 기대고 있는 가정·추정 상태와 '틀리면 무엇이 달라지나'.
  - 후보(규칙 순서): 요청에 넣은 보류 → 선상 설치로 계산 → 새 자재 리드타임(일정 위험) → 선주와 인도일 조정(노출 금액) → 변경 원인 미입력(지체상금이 붙음) → 설계변경 사전 점검 '확인 필요'(`docs/engine.md`(사전 점검) 5절) → 기록의 확인 목록(판단 불가·엑셀 경고) → 사전 점검 '주의'·'점검 불가' → 판단이 걸린 상태(근거 없음 → 계획 추정 → 일주일 넘게 확인 안 함, 보류 권고 발주·발주 먼저, 끝난 공정은 뺌, 판단 불가로 이미 있는 엔터티는 뺌).
  - 사전 점검 후보는 기록 본문의 항목 글을 그대로 쓰고(같은 유형 합성 NCR 건수가 있으면 '같은 유형 합성 NCR n건(합성 묶음(시연))'), '틀리면'은 숫자 없는 위험 이유다. 검사는 항목 글을 기록 값의 이름으로, 건수를 기록 값의 개수로 허용한다.
  - `computed = true`는 '틀리면'의 숫자가 엔진이 그 가정을 바꿔 **이미 계산해 둔 값**일 때만이다: 선상 설치 선택지(반대 방식의 탑재·출구 지연과 총액 차이), 일정 위험(리드타임 범위 끝의 출구·인도 지연), 노출 금액(원인 미입력일 때의 지체상금). 그 밖은 숫자 없는 일반 문장이다.
  - **확인할 것은 다시 계산하지 않는다**: 기록의 지도·계산 판이 지금 활성 지도와 다를 수 있어(실시간 시연 세계는 날마다 지도 ID가 바뀜) 활성 색인으로 다시 분석하면 오류가 나거나 결정 대화상자의 숫자(기록 본문)와 달라진다(더 저렴한 대안 권고만 위 조건에서 예외).
- **AI 고르기**(`ripple/brief/pick.py`, 작업 `brief`, `docs/input.md`(외부 AI) 1절): 합성 데이터 기록이면 후보 키 목록과 서버가 만든 글을 주고 **확인할 것의 선택·순서만**(최대 3개) JSON으로 받는다. 후보 밖 키·중복·빈 답·3개 넘음·형식 오류·실패·6초 넘음은 규칙 순서로 간다. `picked_by = ai`는 그 경우에만이다(화면 칩 '확인 항목 AI 선택').
  - AI를 부를지는 **기록 본문의 데이터 모드**로 정한다 — 활성 지도가 합성이어도 관리자는 실데이터 기록을 열 수 있어서, 실데이터 기록은 본문이 외부로 나가지 않는다(설정이 실데이터 모드여도 부르지 않음).
- **검사**(`ripple/brief/audit.py`, 계약 검증이 보지 않는 것): 줄은 change · loss · advice 순서로 정확히 3개, 확인할 것 키 고유, 글 속 숫자(날짜·요일·D-n·배율·금액·일수·개수)가 모두 기록 본문 값, 계산하지 않은 '틀리면'에 숫자 없음. 규칙 결과가 걸리면 500(도우미만 못 보이고 결재는 그대로), AI 결과가 걸리면 규칙 결과로.
- **기억**: 같은 기록 · 같은 개정(같은 본문이 다른 개정으로 다시 올 수 있어 — A → B → A, 응답에 개정이 적힘) · 같은 업무상 오늘(자정에 D-n이 바뀜) · 같은 AI 경로(모델·설정 판)면 프로세스 메모리의 결과를 다시 쓴다(15분, 200개) — 다시 열 때 AI를 또 부르지 않게. 화면도 한국 시간 날짜를 불러오기 열쇠에 넣어 자정이 지나면 다시 부른다.
- **실패 기록**: 과거 사례 찾기 예외, AI 결과의 검사 불통과, 규칙 도우미의 검사 실패(500)는 설계변경·기록 ID와 함께 경고 로그로 남긴다(결재는 그대로).
- **비슷한 과거 사례**: `build_brief`가 받는 `CaseFinder`(분석 결과 → `PastCases`)가 채운다. API는 **기록이 깔린 지도** 기준으로 고른다(`ripple/api/past_cases.py` `finder_for`): 합성 기록은 그 기록 지도(상태 갱신 지도는 계보 시작)의 합성 묶음(아래 '합성 과거 사례'), 실데이터 기록은 실데이터 묶음(합성 사례 없음), 기록의 지도를 서버가 모르면(지난 날의 실시간 시연 세계 기본 지도 등) 그 기록의 기준일로 생성기 세계를 다시 만들어 지도 ID가 기록과 같을 때만 묶음을 만든다(백그라운드, `building` → `ready`, 지도 ID로 기억). 다르면 `unavailable` — 다른 지도의 사례를 끌어오지 않는다.
  - 실데이터 결과에는 `find_cases`가 합성 묶음을 쓰지 않는다(묶음을 고르는 쪽과 따로 막는 이중 차단).
  - 묶음을 만들다 실패하면 60초 뒤 다음 미리 만들기·요청 때 다시 만든다(그 사이에는 `unavailable`, 요청마다 만들지 않음).
  - 합성 묶음은 약 6초 걸려 작업 공간이 기본 지도를 깔 때(시작 · 날짜 전환은 바꿔 끼운 뒤에만) 백그라운드로 미리 만든다. 묶음 선반은 프로세스에 하나를 같은 엔진 입력(규칙표·비용 파라미터)끼리 나눠 쓴다(검사가 앱을 여러 번 만들어도 같은 세계를 한 번만 만들게).
  - 만드는 중(`building`)에 만든 도우미는 기억하지 않고, 화면은 4초 뒤 다시 불러(5번까지) 사례를 채운다. 묶음 상태 `building`(기본 지도를 깔 때 백그라운드로 만드는 중)이면 화면은 '과거 사례 준비 중' 한 줄, `unavailable`(생성 세계와 다른 지도)이거나 0건이면 그 절을 그리지 않는다.
  - 화면은 접어서 시작한다(요약 한 줄과 '사례 n건 보기') — 카드가 핵심 수치 카드를 화면 밖으로 밀지 않게.
- 권한: **승인 권한(팀장)만**(담당자·체험은 403) — 결재하는 사람의 카드이고 외부 AI를 부를 수 있어서 화면에서만 숨기지 않고 경로에서 막는다. 화면은 **팀장 + 검토·보류 중**일 때만 그린다.
- 검증: `tests/checks/brief.py`(개발 분할 40건 + 가정 계산 변형으로 순서·숫자 출처·결정성·권고 우선순위·computed 값 = 엔진 값, 검사 함수 반례, loss 분기, 가짜 모델 AI 고르기, 실데이터·API 409/404·기억), 권한 행렬은 `tests/checks/auth_api.py`, 화면은 `web/src/lib/brief.test.ts`·`components/records/brief/DecisionBriefCard.test.tsx`·`DecisionBriefPanel.dom.test.tsx`.

### 14. 결재선·무비용 담당자 처리·결재 소요 (계약 1.33.0, `ripple/records/approval.py`)

현장 답변: 추가 비용 건은 담당자 → 파트장 → 팀장 → 본부장·실장 결재 뒤 진행하고, 결재 라인별 1~2일 안에 결재하는 것이 관례다. 그래서 결재선을 두고, 결정 기한 앞에 결재 소요를 둔다.

- **결재선**(추가 비용 건) = 파트장(`part_lead`) → 팀장(`admin`) → 본부장·실장(`executive`). 파트장·본부장 역할(계약 `Role.PART_LEAD`·`EXECUTIVE`)은 결재만 하는 승인 권한이고, 구성원 관리·지도 전환·가져오기는 팀장이다.
  - **검토 요청 때 결재선을 그 검토에 고정**한다(`ReviewInfo.steps`, 감사 줄 `steps`). 지금 단계는 `ReviewInfo.step`(1부터). 상수가 바뀌어도 진행 중 검토의 단계 수는 그대로다.
  - 단계 승인은 다음 단계로 넘긴다(상태는 검토, 버전 +1, 검토 순번·요청자 그대로). 마지막 단계 승인이 승인이다. 반려는 어느 단계에서든 검토를 끝내고, 보류는 그 단계에서 이어진다(보류 뒤 승인은 다음 단계로).
  - 단계마다 승인 조건(지도·계산 판·확인 목록 전부 체크 + 사유)이 같다. 계산 판이 바뀐 결재는 단계마다 반려·보류만이다(1절).
  - 결정할 수 있는 사람: 지금 단계의 결재자, 또는 **팀장 전결**(팀장이 파트장·본부장 단계를 대신 결정 — 감사 세부 `proxy = true`와 원래 단계 `step`, 화면 '전결'). 개발 모드는 모든 단계를 자기 단계로. 요청자 본인은 어느 단계에서도 `self_decision`.
  - 검토 취소는 요청한 사람이나 팀장만.
  - 판 3까지의 검토는 팀장 한 단계(1/1단계)로 읽는다(4절).
- **무비용 담당자 처리**(`settle`): 비용 줄이 도면 개정(`R-D01`)뿐이고 판단 불가 줄(상태를 몰라 범위로 낸 줄)·지체상금 노출 금액이 없으며 **판정이 승인 가능**인 개정(`approval.no_cost`, 비용 줄이 없어도 무비용). 비용이 도면 개정뿐이어도 판정이 경고·검토 필요(구역 출구 지연·자재 납기 위험 등)면 결재선으로 간다. 합성 300건 중 22건(개발 11 · 평가 11).
  - 담당자가 분석 → 승인으로 바로 처리한다(감사 세부 `no_cost`). 결재자의 승인(`approve`)과 다른 행동이라 '담당자 자기 승인 403(`self_decision`)'은 그대로다.
  - 조건: 기록 권한 · 분석 상태 · 무비용 개정(아니면 409 `invalid_transition`) · 지도·계산 판 같음 · 확인 목록이 있으면 전부 체크 + 사유. 그 뒤 실행 시작·종료는 같다.
  - 무비용 개정도 검토 요청은 받는다(결재선 그대로 — 담당자가 결재를 받고 싶으면 올릴 수 있게).
- **결재 소요·결재 올릴 기한**(`ApprovalPlan`, 계약 1.33.0, 엔진 밖 설정 — 분석 결과·관문 값은 그대로): 단계당 근무일 1~2일(대표 2). 규칙은 `ripple/records/approval.py` **한 곳**이고 읽을 때 계산하며 저장하지 않는다. 같은 값이 **분석 응답**(`AnalysisResult.approval_plan` — 엔진은 채우지 않고 분석 API가 덧붙임, 비면 직렬화에서 빠져 기록 본문·기록 ID·분석 ID와 무관 — 기록 전 분석에서도 보임), 상세(`EcnDetail.approval_plan`), 결재함 줄(`InboxItem.approval_plan`), 기록 조회(`EcnRecord.approval_plan` — 판단 리포트)에 실린다. 화면·엑셀은 이 값만 쓴다(화면·엑셀 쪽 결재 상수 없음).
  - 결재선(`line`, 단계 이름 목록 — 1.33.0 선택 필드) = 검토 전이면 검토를 요청할 때 고정될 결재선, 검토 중이면 그 검토에 고정한 결재선. 화면(검토 요청 창)은 결재선 글을 이 값과 단계당 근무일로 만든다.
  - 남은 단계 = 검토 전이면 결재선 전체(무비용이면 없음), 검토 중이면 지금 단계부터(무비용 개정을 검토 요청했어도 그 검토의 결재선 — 결재 기간 `line_steps`·보류 권고 문구도 결재선 기준).
  - 결재 올릴 기한 = 그날부터 근무일(남은 단계 × 2)이 지나도 결정 기한을 넘지 않는 **마지막 근무일** — 불변식 `plus_workdays(결재 올릴 기한, n) ≤ 결정 기한`. 결정 기한이 토·일이면 그날 이하 마지막 근무일(금요일)에서 근무일을 뺀다(토요일에서 바로 세면 결재가 다음 월요일에 끝나 하루 늦음). **주말 제외·공휴일 무시**. 탐색 기간 안 손실이 없으면(none_in_horizon) 없다.
  - **지남**(`late`) = 오늘 올려도 결재가 결정 기한 안에 끝나지 않음 — `plus_workdays(업무상 오늘(11절 날짜 기준), n) > 결정 기한`. 업무상 오늘이 평일이면 결재 올릴 기한이 오늘보다 앞인 것과 같고, 토·일이면 그 앞 금요일에 올린 것과 같다(결재 올릴 기한이 바로 앞 금요일이어도 주말에는 아직 지나지 않음 — 날짜 비교로 세면 실시간 세계·실데이터에서 주말마다 거짓 '지남'이 나온다). 지났으면 '오늘 올려도 결정 가능일은 ○월 ○일(업무상 오늘 + 같은 근무일) — 그날 추가손실 ○원(기록된 곡선 대표값)'.
  - **단계당 1일이면**(`submit_by_low`·`late_low`, 1.33.0 선택 필드): 같은 규칙으로 근무일을 남은 단계 × 1(`days_per_step_low`)로 센 결재 올릴 기한과, 단계당 1일로 결재돼도 오늘 올려서는 결정 기한을 넘는지(`late`와 같은 꼴). 대표 기한이 지났어도 빠른 결재로 결정 기한 안에 들 수 있는지 보인다(화면 예: '결재 올릴 기한 10월 27일(화)(단계당 2일) 지남 · 단계당 1일이면 10월 30일(금)까지'). 늘 대표 기한 이후이고, 단계당 1일 기한이 지났으면 대표 기한도 지났다. 불변식 `plus_workdays(submit_by_low, 남은 단계 × 1) ≤ 결정 기한`과 최대성(다음 근무일은 기한을 넘김), 업무상 오늘의 모든 요일에서 지남 판정을 검사가 본다.
  - **결정 기한의 근무일**(`decide_by_workday`, 1.33.0 안, 선택): 결정 기한 이하 마지막 근무일(토·일이면 그 앞 금요일, 공휴일 무시) — 확정 단추가 주말을 권하지 않게 쓴다(결정 기한 표시는 그대로). 손실이 없으면(none_in_horizon) 없고, 그날이 업무상 오늘보다 앞이면(업무상 오늘 토요일 · 결정 기한 일요일 등) 없다 — 지난 근무일을 권하지 않는다.
  - **화면 표시**(`web/src/lib/approval.ts` `submitLine` · `lib/deadline.ts` `deadlineWorkday`, `DESIGN.md` 13·15절): 결정 기한 카드·결재함 줄의 결재 올릴 기한 줄에 단계당 1일 날짜를 함께 적고('… 10월 29일(목) · 단계당 1일이면 11월 3일(화)까지 (결재 3단계 · 근무일 3~6일)'), 대표만 지났으면 주의 색으로 '… 지남 · 단계당 1일이면 10월 30일(금)까지', 둘 다 지났으면 '… 지남 · 빨라야 ○월 ○일(요일) 결정'(위험 색). 결정 기한이 토·일이면 확정일 단추가 근무일('확정일을 11월 6일(금)로')을 가리키고 결정 기한 보조 설명 끝에 '근무일 기준 11월 6일(금)'을 붙인다(D-n·날짜는 그대로, 근무일이 기준일보다 앞이면 붙이지 않음). 결정 기한이 토·일인데 근무일이 없으면(기준일 뒤에 근무일이 없음) 주말 날짜를 권하지 않게 확정일 단추 없이 '확정일 · 결정 기한 안'만.
  - **보류 권고의 결재 기간**(`holds`, 보류 권고마다): 결재 기간 = 기준일부터 근무일(결재선 전체 단계 × 대표 2, `line_steps`). 권고 보류 마지막 날이 그보다 뒤면 '결재 중(약 6근무일 — 결재 3단계 × 1~2일)에는 보류 유지 가능 · 권고 h일까지 보류 시 공급사 협의 필요', 같거나 앞이면 '권고 h일은 결재 기간(…)보다 짧은 보류 · 그 안에 결재 완료 시 손실 회피'(요약 복사용 짧은 꼬리 `short`). 무비용이면 '담당자 처리 — 결재 없음'. 엔진 보류 권고(`max_hold_days`·`hold_until`)는 그대로다.
- **결재함**: 보는 사람의 결재 단계 건만(파트장 = 파트장 단계, 팀장 = 팀장 단계, 본부장 = 본부장 단계, 개발 모드 = 전부 — `api/routes/manage.py`가 역할로 거름). 팀장에게는 그 아래 **'다른 단계에서 기다리는 건(전결 가능)'** 묶음(`ManageOverview.proxy` — 파트장·본부장 단계 건, 그 단계가 시작된 때 `InboxItem.step_since`로 대기 일수)을 더 싣고, '전결 열기'로 업무 화면에서 그 개정의 분석을 보며 전결한다(감사 `proxy`). 파트장·본부장에게는 묶음이 없다. 줄마다 지금 단계 · 결재선 · 앞 단계 승인(사람·전결) · 남은 결재 계획.
  - 현황의 결재 대기·마감 임박은 모든 단계를 센다. 결재 대장 엑셀은 화면과 같은 결재함 줄이다: 결재함(내 결재 · 팀장의 전결 묶음 줄은 '전결 가능') · 지금 단계(n/전체) · 결재선(단계 수) · 승인한 단계(사람, 전결 표시) · 단계 대기 시간(`InboxItem.step_waiting_hours`) · 남은 결재 올릴 기한 · 결재 올릴 기한(단계당 1일) · 지남 · 기한 경과 시 결정 가능일(결재 계획 그대로). 지남 칸은 화면의 주의·위험과 같은 뜻으로 가른다 — 대표(단계당 2일) 기한만 지났으면 '지남(단계당 1일로는 가능)', 단계당 1일로도 지났으면(또는 단계당 1일 기한이 없는 옛 계획) '지남'.
- **성과**: 결정 = 마지막 단계 승인 · 어느 단계든 반려·보류(중간 단계 승인은 결재선 진행이라 세지 않는다. 반려는 어느 단계에서든 검토를 끝내고, 보류도 그 단계 결재자의 결정 행위라 센다). 처리 시간은 단계마다 그 단계가 시작된 때(검토 요청 또는 같은 검토의 앞 단계 승인)부터 결정까지 — 전체 중앙값과 단계별 중앙값(`Performance.steps`). 무비용 담당자 처리 수(`settled`).
- **시연**(`docs/operations.md`(서비스) 7절): 파트장·본부장 가상 계정(`part-lead` 이파트장 · `executive` 최본부장)은 빠른 로그인 고정 계정이다(계약 `QuickLogin.role` 담당자·파트장·팀장·본부장, 비밀번호 없음, `RIPPLE_DEMO_PASSWORD`는 읽지 않음). 화면 단추는 담당자·파트장 둘이고(10-30), 팀장·본부장 단계는 결재선 진행 표시로 보인다. 팀장 계정으로는 전결로 결재선 끝까지 결정할 수 있다.
- 범위 밖: 금액별로 결재선을 줄이는 전결 규정, 결재선을 건마다 고르는 일, 공휴일 달력, 결재 단계별 알림 발송.

### 2. 숫자와 문장

- 본문은 서버 메일 템플릿(숫자·수량 표현 없는 합니다체 문장, 문단 머리 `■`·항목 `-`도 템플릿)과 수치 블록만 쓴다.
  - 수치 블록은 공식 메일에서 `라벨: 값` 꼴(끝맺음 없는 명사형)이다.
  - **본문의 숫자는 모두 수치 블록에서 나오고 E4 검출기가 결과 값과 대조한다**(설명·알림과 같은 규칙).
- 협력사 메일에는 **보류 유지 가능 기한 말고는 내부 계산값(비용·결정 기한·지연)을 넣지 않는다**. 사내 협력사 작업반 메일에는 **결정 기한**(확정 예정 시점 — 작업 지시가 언제 다시 올지)만 넣고, 그 밖의 사내 메일에는 수치를 넣지 않는다(검사 `tests/checks/mail.py`).
- **보류 유지 가능 기한**(`hold.until`) = 분석 기준일 + 보류 가능 일수(`docs/engine.md`(비용·일정) 8-3).
  - 기준일부터 바로 보류할 때 탑재 일정을 늦추지 않고 보류를 유지할 수 있는 마지막 날이다.
  - **이날까지 보류 결정을 미뤄도 된다는 뜻이 아니다** — 메일에도 이 전제 문장을 기한 앞에 적는다('보류 결정 기한'이라 부르지 않는다, 설명·알림 공통).
- 대상이 많으면(한 문단 30개) 문단을 나눈다(머리는 첫 문단에만).

### 3. 시연용 가상 연락처

- `params/contacts_v1.yaml`: 합성 지도 협력사 넷(supplier_id 열쇠)·구매·생산관리·도면 분야(hull·piping·outfitting·machinery·design)의 지어낸 회사·사람.
  - **이메일은 모두 예약 도메인 `.example`**(RFC 2606, 배달되지 않음) — 아니면 계약 검증이 시작을 거부한다.
- **합성 모드 지도에만 붙인다**(`AssistantResources.build`). 실데이터 지도(엑셀 가져오기)에는 붙이지 않고 받는 사람을 비운다(사용자가 메일 창에서 적는다). 실제 연락처 열을 엑셀 양식에 더하는 일은 아직 하지 않았다.
- 화면은 가상 연락처 초안에 '시연용 가상 연락처(.example — 실제 배달 없음)'를 적는다.

### 4. 메일 도구로 열기(화면)

- **Gmail 쓰기 창 하나만** 쓴다(`mail.google.com/mail/?view=cm`, 새 탭). 메일 앱(mailto)·Outlook은 넣지 않는다.
  - 초안이 주소로 Google에 가므로 **합성 데이터 지도에서만** 연다 — 실데이터 지도는 열기 단추가 없고 복사만 된다.
- **카드**: 머리 띠(수신 구분 칩 · 받는 쪽 이름 · `Gmail로 쓰기` · `복사`(받는 사람·참조·제목 머리 + 본문)) · 접힌 요약(받는 사람 이름 한 줄 · 제목) · `본문·참조 보기`로 주소·참조 · 본문 전체 · 통보 기록(모양은 `DESIGN.md` 6절 AI 비서).
- **메일 보내기… 창**(한 차례의 초안 전부): 초안 고르기(체크) · 줄마다 `열기` · `다음 메일 열기 (n/m)` · `모두 복사` · 왼쪽 `닫기`.
  - `다음 메일 열기`는 클릭 한 번에 한 통이다 — 한 번에 여러 창을 열면 브라우저가 팝업으로 막는다.
  - 창이 열렸으면 '열림'(보냈다고 단정하지 않는다), 팝업이 막혔으면 표시하지 않고 팝업 허용을 안내한다.
- **본문이 길 때**: 주소 길이 한도(7,000자, 한글은 퍼센트 인코딩으로 약 9배)를 넘으면 본문 없이 열고 본문을 클립보드에 복사한다.
  - 그 초안은 '붙여 넣기 기다림'이 되고, `붙여 넣기 완료`를 누르기 전에는 다른 초안 열기·복사·모두 복사를 막는다(카드·창 공통 잠금 — 다음 본문이 클립보드를 덮어쓰지 않게).
  - `본문 다시 복사`·복사 실패 안내가 있다.
- **통보 기록**(1.28.0): 지금 상세에 보이는 분석의 카드 아래에 `통보 기록` 줄 — 마지막 단계와 날짜('보냄 10월 21일(수) · 3일째 수령 확인 없음')와 날짜 입력 · `보냄` · `수령 확인` · `회신 받음`.
  - 누르면 고른 설계변경의 최신 개정에 감사 줄(`action = notice`)로 남는다(`POST /api/ecns/{ecn_id}/notices`, `docs/records.md`(기록·결재) 7절, 받는 조건은 기록·결재 편 3절). 결재 흐름을 막지 않는다.
  - 고칠 수 없다(잘못 적었으면 같은 단계를 새 날짜로 다시 적는다).
  - 기록이 없으면 '결재 띠에서 기록을 남기면…' 안내, 기록 권한이 없으면 줄만 보인다.
  - 이력 탭·리포트 이력에 '통보 기록 · 협력사 SUP-VL1 · 회신 받음 10월 23일(금)'으로 보인다.

### 6. 현장 통보문 번역 초안(1.36.0)

현직자 멘토링: 외국인 근로자는 일상 한국어와 달리 전문 기술 용어를 알아듣기 어렵다. 화면 전체를 다국어로 바꾸지 않고,
**사내 협력사 작업반에 보내는 통보 메일(1절 표의 작업반 줄)만** 한국어 원문과 함께 번역 초안을 붙인다(`EmailDraft.translations`).

- **외부 AI 없이 결정적**이다(같은 입력 → 같은 출력, `real` 모드도 같다 — 외부 호출 금지 규칙 그대로).
  - 글 블록: 한국어 템플릿 ID마다 언어별 문장(`params/glossary_v1.yaml` `sentences`)에 엔터티 이름을 끼운다. 자리(`{0}`) 수는 한국어 템플릿과 같아야 한다.
  - 엔터티 이름(공정·부재·작업반·보내는 조직): 조선 용어집(`terms`)으로 말마다 바꾸고(길게 맞는 말 먼저 — 판넬조립 > 판) 원문을 괄호에 둔다('T31C panel assembly (T31C 판넬조립)') — 현장 서류의 한국어 이름과 맞춰 보게. 낱말 순서는 한국어 그대로다(용어 대역).
  - 붙어 쓴 한글 덩어리는 용어 연쇄로 끝까지 빈틈없이 덮일 때만 바꾼다(판넬+조립). 앞머리만 맞으면 덩어리 전체를 원문 그대로 둔다 — '배관재'·'평형수탱크'·'판정'을 '배관'·'평형수'·'판' + 나머지로 쪼개지 않는다.
  - 용어집에 없는 말(고유 이름 '한빛'·'가람조선' 등)은 한국어 그대로 두고 `untranslated`에 남긴다. 지어내지 않는다.
  - 관련 건 줄의 변경 제목은 사용자가 쓴 자유 문장이라 번역하지 않고 원문 표시(`[Korean]`·`[Tiếng Hàn]`)를 붙인다.
  - 수치 블록은 언어별 라벨 + 결과 필드 값. 날짜는 `YYYY-MM-DD`(원문과 같은 날·같은 숫자). 언어 문장이 없는 블록은 원문 그대로 둔다.
  - 끝에 '주요 용어' 문단: 원문에 나온 용어집 용어(두 글자 이상, 12개까지, 용어집 순서)를 '한국어 – 번역'으로.
- 문단·블록은 원문과 하나씩 맞는다(같은 템플릿 ID·수치 키·엔터티). **숫자·블록 번호·날짜는 원문과 같다**(검사).
- 언어: 영어(`en`)·베트남어(`vi`). 우즈베크어·네팔어·태국어 등은 **데이터만** 더하면 된다 — `languages`에 코드 하나, `sentences`·`metrics`·`terms`의 모든 줄에 그 언어 값.
  빠진 줄·숫자가 든 문장이 있으면 계약 검증이, 자리 수가 틀리면 `glossary_problems`가 앱 시작을 막는다.
- **원문 병기 표기**: 메일 본문의 번역 머리에 그 언어 문장 + 한국어 문장(합니다체 — '번역과 한국어 원문이 다르면 원문이 우선합니다.'). 화면에는 '초안' 표기를 두지 않는다(11-03 사용자 결정), 용어집 밖 원문 유지 말 한 줄만.
- 화면(메일 카드): 머리 띠 바로 아래(접힌 카드에서도 보임) '통보문 언어' 단추 — `한국어`(기본) · `English` · `Tiếng Việt`, 번역을 고르면 번역만(한국어 원문을 덧붙이지 않음 — 11-04 사용자 결정), 원문 유지 말 한 줄('용어집 미등록 · 원문 유지: 한빛, 가람조선').
  - 카드의 제목·본문·`복사`·`Gmail로 쓰기`가 고른 보기를 쓴다. `메일 보내기…` 창은 한국어 원문 그대로다.
- 한계: 문장·용어는 현직자·원어민 검토 전 초안이다(특히 베트남어 낱말 순서와 공정 이름). 작업반 밖 메일(협력사·제작·도면)은 번역하지 않는다.
- 버전 맞춤: 번역 초안은 1.36.0 서버만 싣는다. 코드를 받은 뒤 번역을 반영하려면 API를 다시 시작한다(점검 메모는 `docs/operations.md`).

### 7. 상세에서 통보문 보기(1.37.0)

작업반 통보문은 AI 비서 분석 차례에서만 만들어져, 목록에서 연 설계변경(예: ECN-D-0119)의 상세에서는 볼 곳이 없었다.

- **API** `POST /api/analyses/notices`(본문 = 분석 요청, `?target=crew`면 그 받는 쪽만) → `AnalysisNotices`(`analysis_id` · `notifications`).
  - 보던 분석의 요청 그대로 다시 분석해(엑셀 내보내기와 같은 길 — 같은 요청이면 같은 결과) **AI 비서와 같은 규칙**(`ripple/explain/compose.py` `notifications`)으로 초안을 만든다. 작업반 메일의 번역 초안·시연용 가상 연락처 규칙도 같다.
  - 외부 AI를 부르지 않는다(결정적, `real` 모드도 같다). 엔진 계산은 바뀌지 않는다(분석 결과를 읽기만). 권한은 분석과 같다.
- **화면**: 상세 할 일 → 사전 점검의 '현장 통보 필수' 줄 옆 `통보문 보기` → 대화상자에 비서 칸과 같은 메일 카드(언어 전환 · 복사 · Gmail로 쓰기 · 통보 기록). 처음 열 때 한 번 받고 같은 분석이면 다시 받지 않는다.
  - 다시 계산한 분석 ID가 보던 분석과 다르면 '지금 지도 기준으로 다시 계산한 통보문 · 보던 분석과 조건 다름'. 보낼 작업반이 없으면(직영·수행 주체 모름만) 빈 안내.
- 검사: `tests/checks/api.py`(같은 요청 → 같은 분석 ID, `target=crew` = 비서 규칙의 작업반 초안 그대로·번역 포함, 받는 쪽을 주지 않으면 전부).

## 합성 과거 사례

팀장이 결재할 때 '비슷한 과거 사례 3건'과 한 줄 요약을 보여 주는 재료다(`ripple/cases`, 결정 도우미 계약 `PastCases`).
실제 결재 이력이 없으니 **합성 모드에서는 시연용 합성 과거 사례 묶음을 만들고, 화면에 늘 '합성 과거 사례'로 표시한다**
(`synthetic=True`). 실데이터 모드에서는 합성 사례를 만들지 않는다.

### 1. 어떻게 만드나(합성 모드)

- **세계**: 작업 공간 지도(상태 갱신 지도면 계보 시작 = 뿌리 기본 지도)의 기준일로 생성기 세계를 다시 만들고
  (`generate(config, scenario_date)`), 만든 지도 ID가 그 지도와 같을 때만 쓴다. 다르면 빈 묶음(`unavailable`).
- **재료**: 그 세계의 개발 분할 설계변경 중 **화면 샘플이 아닌 것**(약 180건)에서 연산 비율대로 30건
  (`params/cases_v1.yaml` `count`). 평가 분할은 최종 인증용이라 쓰지 않는다. 사례 번호는 `PAST-` 접두.
  - 엔진이 거부하거나 예측·실적이 0원 이하(절감 변경)인 재료는 건너뛴다 — 계약의 실적은 0 이상이다.
  - 변경 방향과 목적이 모순되는 재료는 뺀다(두께·강종을 낮추는데 목적이 중량 조정이 아님, 치수를 늘리는데 목적이 중량
    조정). 생성기가 연산과 목적을 따로 뽑아 생기는 짝이고 생성기는 그대로 둔다. 남은 재료의 목적은 방향과 맞아
    '같은 변경 목적'으로 비교한다(`ripple/cases/materials.py`).
  - 제목은 묶음 안에서 늘 다르다: 블록 코드로 시작하지 않으면 앞에 붙이고('E21C 평형수 배관 경로 변경…'), 그래도 같으면
    바꾸는 부재 번호를, 그래도 같으면 사례 번호를 덧붙인다.
- **예측(엔진)**: 기준일 분석의 추가손실 곡선에서 결정한 날의 총변경비용·구역 출구 최대 지연, 추가손실 0 마감일.
  결정 요청(확정일 = 결정한 날, 발주 보류)을 다시 분석하면 같은 값이다(검사 `cases`).
- **실적(숨긴 실제 모델)**: 같은 세계의 `ripple/generator/actuals`(`docs/data.md`(생성기) 6-1)가 그 결정
  (확정일·보류 발주)으로 계산한 실제 비용·구역 출구 지연. 늦게 정한 효과도 이 모델이 계산한다 — 오차 분포를 따로 정하지 않는다.
  반려·결정 보류는 실행하지 않아 실적이 없다(None).
- **시드 고정 가정(근거 없음, `params/cases_v1.yaml`)**: 결정 종류(요청대로 승인 0.72 · 발주 보류 뒤 승인 0.15 · 반려 0.08 ·
  결정 보류 0.05, 할 수 있는 것 중에서)와 결정 시점(마감 뒤 30%: 1~10일 늦게, 마감 전: 0~10일 먼저, 마감이 없으면 기준일 +
  0~20일). 이 둘만 난수이고 사례마다 `(시드, ECN)`으로 정해 같은 지도면 같은 묶음이다.
  - 넣지 않은 것: 대안으로 승인(대안 계산을 끄고 만든다 — 30건에 대안까지 계산하면 너무 오래 걸림), 선상 설치(숨긴 모델이
    다루지 않음).
- **한 줄 교훈**: 서버 템플릿 중 데이터와 맞는 것만 — '결정 기한보다 n일 늦게 결정 — 예측 비용 x원 증가'는 실제로 마감
  뒤였고 엔진 곡선에서 마감일보다 늘었고 숨긴 모델 실적도 마감일에 정했을 때보다 컸을 때만. 그 밖에 반려·보류, 발주 보류로
  줄인 금액, 범위 초과, 마감 안 결정.
- **만드는 때**: 30건에 로컬 약 5초(엔진 분석이 곡선 60일을 하루씩 평가)라, 작업 공간이 기본 지도를 깔 때(시작·날짜 전환)
  `CaseShelf.prepare`로 백그라운드에서 미리 만들고 뿌리 지도 ID마다 기억한다(최근 3개). 그 전에 온 요청은 기다리지 않고
  빈 답을 받는다(`CaseLibrary.status = building` — 화면은 '과거 사례 준비 중').

### 2. 비슷한 정도와 요약

- **같은 변경 연산 종류만** 본다. 점수 = 같은 블록 6 · 같은 구역 2 · 같은 배관 계통 2 · 같은 변경 목적 1 · 크기 가까움 0~1
  (두께 차·치수 비율·스풀 수·관통 지름, 강종·사양은 같은지). 문턱 2 미만은 빼서 억지 사례를 보이지 않는다. 같은 블록
  사례가 늘 앞에 온다(같은 블록 최소 8 > 다른 블록 최대 6). 같은 변경(연산이 똑같음)·같은 ECN 번호는 뺀다.
- **순서**: 같은 블록 무리 → 다른 블록 무리, 무리 안에서는 **실적이 있는 사례(승인)를 앞에** 두고 반려·보류(실적 없음)는
  같은 무리의 실적 있는 사례가 모자랄 때만, 그다음 점수 순(같으면 사례 번호 순).
- 생성 자료는 변경 원인이 늘 비어 있어 원인 대신 변경 목적(intent)을 쓴다.
- `same`은 사람이 읽는 같은 점('같은 두께 변경', '같은 블록 B31P', '같은 화물탱크 구역', '같은 평형수 계통',
  '같은 목적(강도 보강)', '같은 목표 강종(AH36)', '비슷한 크기(두께 +2.0mm)') — 같은 말을 두 번 쓰지 않는다.
- **요약은 건수와 사실만**: '비슷한 3건 중 1건은 실적이 예측 초과 · 1건은 결정 기한 뒤 결정' '예측 초과'는 화면
  사례 줄의 차이 %와 같은 기준(반올림한 % > 0, `notes.grew`)이라 '예측 초과'와 '(±0%)'가 함께 나오지 않는다. 오차율 중앙값·%는
  쓰지 않는다 — 합성 실적의 오차는 숨긴 모델에 넣은 잡음을 다시 잰 것이라 정확도로 읽히면 안 된다(E2a 해석 주의와 같은
  이유). 사례 한 건의 예측 → 실적 값은 보여도 된다.
- 숨긴 모델은 평가(E2a·E2'·E7)의 정답과 같은 모델이다. 이 사례를 보고 엔진 파라미터를 고치지 않는다(개발 분할 규칙과 같음).

### 3. 실데이터 모드

- 합성 사례를 만들지 않는다. 기록 중 **종료 상태 · 실적(`OutcomeEntry`) 있음 · 승인한 개정의 본문이 실데이터**인 ECN만
  과거 사례다(`synthetic=False`, 없으면 빈 묶음). 요청마다 기록·실적 저장소에서 바로 만든다(지도 캐시 아님).
- 예측 = 승인한 개정의 분석 결과(총변경비용·구역 출구 지연), 실적 = 지금 실적 값, 결정 날짜 = 승인 감사 줄(11절 날짜 규칙).
- 교훈은 범위 초과·마감 안/뒤 결정만(마감일에 정했을 때의 실적은 알 수 없어 '증가'를 쓰지 않는다).

## 합성 NCR

설계변경 사전 점검(`docs/engine.md`(사전 점검)) 항목 옆에 '같은 유형 합성 NCR n건'을 보이는 시연 재료다(`ripple/cases/ncr.py`,
계약 `ripple/contracts/ncr.py`, 1.32.0 안에서 추가). **실제 NCR(부적합 보고) 이력이 없어** 합성 모드에서만 만들고, 이 묶음으로
엔진이나 사전 점검 규칙을 검증했다고 말하지 않는다.

### 1. 어떻게 만드나(합성 모드)

- **재료**: 지도 생성기 설정(블록·배관 계통·작업반)과 씨앗, `params/ncr_v1.yaml`(유형 비율·건수·작업반 비율 — 근거 없는 시연용
  가정). 기준일·지도·기록을 보지 않아 실시간 시연 세계에서 날이 바뀌어도 같은 묶음이고, 같은 설정·씨앗이면 같은 묶음이다
  (건마다 `(씨앗, 'ncr', 판, 번호)` 난수원).
- **설계변경 번호를 가리키지 않는다** — 시연 목록·합성 과거 사례의 설계변경과 겹치지 않는다.
- **한 건**: 번호 `NCR-S-0001` · 유형(사전 점검 P-01~P-06과 같은 이름 + 기타 2종: X-01 치수·취부 오차, X-02 자재 착오) · 분야
  짝(원인 분야 → 상대 분야: 선체·배관·선장·기장·전장) · 발견 단계(블록 단계) · 조치 수행 주체(그 단계 공정을 맡는 작업반 이름 또는
  직영, 탑재는 직영) · 원인 한 줄 · 조치 한 줄 · `synthetic = true`.
- 원인·조치 글은 유형마다 현직자 사례 유형을 일반화한 서버 템플릿이다(블록 코드·계통 이름만 끼움, 지어낸 숫자
  없음).

### 2. '합성 묶음(시연)' 표기와 건수만

- **모든 문장**(원인·조치)이 `[합성 묶음(시연)]`으로 시작한다(계약이 표기 없는 문장을 거부). 요약도 `label = 합성 묶음(시연)`.
- **건수만** 보인다: 유형별 건수와 최근 n건(번호가 클수록 최근)뿐이다. 비율·대표 손실 금액·오차율은 만들지 않는다 — 합성
  자료의 숫자가 실제 발생률로 읽히면 안 된다.
- 사전 점검 항목의 `ncr_count`는 이 묶음의 같은 유형 건수다(분석 `POST /api/analyses`와 기록 본문 계산 `api/records.py`
  `record_body`가 같은 건수를 넘긴다). 결정 도우미 글에는 '같은 유형 합성 NCR n건(합성 묶음(시연))'으로만 쓴다.

### 3. 실데이터 모드

- 만들지 않는다: 빈 묶음 + 이유('실데이터 모드 — 합성 NCR 미생성(실제 NCR 이력 미수신)').
- 사전 점검 항목의 `ncr_count`는 늘 없다(API가 넘기지 않고, 엔진도 결과의 데이터 모드로 한 번 더 막고, 계약이 거부).

### 4. API

- `GET /api/ncrs/summary?recent=`(`ripple/api/routes/ncr.py`): 유형별 건수(8종, 0건 포함) · 총 건수 · 최근 n건(기본
  `params/ncr_v1.yaml` `recent`, 1~20). 권한은 결정 도우미의 비슷한 과거 사례와 같다(승인 권한 = 팀장, 담당자·체험 403).
  활성 작업 공간이 실데이터 모드면 `available = false`와 이유. 묶음은 프로세스에 하나(처음 쓸 때 한 번 만듦, `api/ncr.py`).
- 검증: `tests/checks/ncr.py`(결정성 · 표기 · 건수만 · 실데이터 차단 · 요약 · API · 분석 응답의 건수), 권한 행렬
  `tests/checks/auth_api.py`.
