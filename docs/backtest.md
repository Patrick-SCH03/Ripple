# 과거 설계변경 백테스트 — 예측 대 실제

실제 과거 설계변경 이력에 Ripple을 적용했을 때 **얼마나 맞는가**를 재는 도구다(현직자가 가장 먼저 검증을 요청한 항목).
사례 하나를 엑셀 한 행으로 받아, 사례마다 엔진이 계산할 수 있는 **작은 지도**를 만들고 `analyze`로 예측한 뒤 실제 결과와 견준다.
코드는 `ripple/eval/backtest/`, 명령은 `scripts/backtest.py`, 성질 검사는 `tests/checks/backtest.py`(묶음 `backtest`)다.

- 숨긴 모델 대비 평가(E2a·E2'·E7, `docs/evaluation.md`)와 달리 정답이 **현장 실적**이다. 다만 사례가 3~5건이고 지도가 작아
  합격 기준을 두지 않는다. 결과는 엔진·파라미터를 어디서 고칠지 찾는 진단으로 쓴다.
- 받은 사례는 **실데이터**다. 다루는 규칙은 7절.
- 기준 판: 엔진 0.12.0 · 계약 1.33.0 · 규칙표 rules-v5 · 비용 파라미터 cost-v8 · 생성기 설정 generator-v4 · 백테스트 기본값
  backtest-v2(결과 파일의 '판' 행이 실행한 판을 적는다).

## 1. 쓰는 법

```bash
uv run python scripts/backtest.py template <양식.xlsx>              # 빈 양식(사례 시트 + 설명 시트)
uv run python scripts/backtest.py template <양식.xlsx> --example    # 가상 예시 3건을 채운 양식(사례 번호 '예시(가상)-n')
uv run python scripts/backtest.py run <입력.xlsx> <출력 폴더>        # backtest_result.xlsx · backtest_result.md
```

- 서버·API 키 없이 돈다. 사례 하나에 0.1초 안팎.
- `run`의 출력 폴더가 저장소 안이면 거부한다(종료 코드 2). 입력 파일이 저장소 안이면 경고만 한다.
- 계산하지 못한 사례(잘못 적은 칸, 발견 단계 없음, 바뀐 것 없음)는 결과에 '계산 불가'와 이유로 남고 나머지 사례는 계산한다.
- 가상 예시(`ripple/eval/backtest/examples.py`)는 실제 회사·호선·사례가 아니다. 양식을 채우는 법과 검사에만 쓴다.

## 2. 입력 양식

'사례' 시트의 한 행 = 한 사례. 1행은 머리글, 2행부터 사례. 열의 단일 출처는 `ripple/eval/backtest/case.py`의 `COLUMNS`다.

| 열 | 형식 | 쓰는 곳 |
|---|---|---|
| 사례 번호 | 글(회사·호선을 알 수 없는 짧은 번호, 예: C1) | 결과에서 사례를 가리키는 유일한 이름. 비우면 '사례 n' |
| 변경 내용 | 글(원문) | **읽지 않는다.** 결과로 옮기지 않음(머리글 노란색) |
| 변경 원인 | 설계 간섭 · 선주 코멘트 · 규정 · 기자재 사양 · 현장 오작 | 요청의 변경 원인(3절) |
| 블록·구역 | 글(원문) | **읽지 않는다.** 결과로 옮기지 않음 |
| 블록 종류 | 평 · 곡 · 선수미 | 블록 형상(재작업 난이도 계수), 블록 무게가 빌 때 기본값. 비면 계수 1(가정) |
| 블록 무게(t) | 숫자 > 0 | 블록 강재 무게, 공정 기간 |
| 발견 단계 | 엔진의 블록 단계 이름(드롭다운) | 기준일(3절). 비우면 계산하지 않음 |
| 바뀐 부재 수 · 재제작 스풀 수 · 개정 도면 수 · 발주 변경 건수 | 0 이상 정수 | 지도 요소(3절) |
| 재제작 방식 | 사내 재제작 · 사외 재발주 · 치수 변경 | 재제작 스풀을 지도에 넣는 방식(3절). 비면 사내 재제작(가정) |
| 추가 공수 최소·최대(MH) | 0 이상 숫자 | 실제 공수(변경 전체 공수) |
| 비용 최소·최대(만원) | 0 이상 숫자 | 실제 비용(원으로 바꿔 씀) |
| 지연 일수(일) | 0 이상 숫자 | 실제 지연 |
| 지연 기준 | 탑재 · 구역 출구 · 인도 | 실제 지연과 견줄 예측. 비면 구역 출구(가정) |
| 수행 주체 | 직영 · 사내 협력사 | 블록 공정의 수행 주체(사내 협력사 = 작업반, 3절) |
| 결정까지 걸린 일수(일) | 0 이상 정수 | 확정일 = 기준일 + 일수. 비면 0일(가정) |

- 숫자 칸은 숫자만 받는다(쉼표는 허용). 글·음수·정수 칸의 소수는 그 사례를 '계산 불가'로 하고 이유를 남긴다.
- 범위는 최소·최대 두 칸이다. 한 칸만 채우면 두 칸이 같은 값, 최소 > 최대는 잘못 적은 칸이다.
- 모르는 칸은 비운다. 빈 칸은 지어내지 않는다 — 지도에 필요한 값은 기본값으로 채우고 '가정'으로 남기며(4절), 실제 값이 비면
  그 비교는 '비교 불가'다(5절).
- 발견 단계는 엔진 단계 이름을 쓴다. 현장 말과의 대응: 선행의장 중 → 선행의장, 선행도장 뒤 → 선행도장, PE(탑재 전 블록
  합치기) → PE, 탑재 뒤 → 탑재. 이름이 바뀐 단계는 옛 이름도 읽는다(판계 = 판넬조립, 조립 = 대조립).

## 3. 변환 규칙 — 사례 칸 → 지도 요소

사례마다 배 1척 · 구역 1개 · **대상 블록 1개와 공정 사슬**(소조립 → … → 탑재 → 구역 출구 → 진수 → 인도)로 된 지도를 만든다.
ID 형식은 생성기(`ripple/generator/ids.py`)를 그대로 쓴다. 지도는 파일로 남기지 않는다.

| 사례 칸 | 지도·요청 | 엔진에서 생기는 것 |
|---|---|---|
| 바뀐 부재 수 n | 보강재 n개(각 0.2t, 강재 발주 품목에 묶임) + **치수 변경** 연산 | 블록 재작업(R-B01, 무게 n × 0.2t) · 도면 개정(R-D01). 발주는 그대로 |
| 재제작 스풀 수 s | 바뀌지 않는 양 끝 스풀 2개 사이에 사슬로 이은 스풀 s개 | 아래 재제작 방식대로 |
| 재제작 방식 = 사내 재제작(빈 칸 포함) | **경로 변경**(빼는 스풀 s, 같은 규격 새 스풀 s), 새 스풀 규격의 표준 리드타임 14일 | 옛 스풀 발주 변경·취소(R-M02) · 자재비 차이 0(같은 수량·단가) · 블록 재작업(옛·새 스풀 무게 모두) · 새 스풀 리드타임 관문(R-S01) |
| 재제작 방식 = 사외 재발주 | 경로 변경, 표준 리드타임을 비워 엔진 파라미터(`lead_time_days.pipe`, cost-v6 60일) | 위와 같고 새 스풀이 늦게 와 관문이 더 늦음 |
| 재제작 방식 = 치수 변경 | 스풀도 바뀐 부재와 같은 **치수 변경** | 블록 재작업 · 도면 개정만(발주 변경·리드타임 없음) |
| 개정 도면 수 d | 바뀌는 부재·스풀을 차례로 d장에 나눠 그림(도면마다 하나 이상) | 도면 개정 d건 |
| 발주 변경 건수 p | 재제작 스풀을 min(p, s)개 품목(품목마다 발주 1건)에 나눔 | 품목마다 발주 변경·취소 1건(확정일 품목 단계의 취소·변경률) |
| 발견 단계 | 기준일(아래) | 블록 단계 → 재작업 배수, 발주 품목 단계, 일정 |
| 블록 무게 W | 블록 강재 무게, 공정 기간 | 일정(기간·여유) |
| 블록 종류 | `Block.shape`(평 `flat` · 곡 `curved` · 선수미 `bow_stern`, 비면 없음). 의장품·전장품 수는 비움 | 재작업 공수 × 형상 난이도 계수(cost-v6 평 1 · 곡 1.3 · 선수미 1.5, 없으면 1), 밀도 계수 1 |
| 변경 원인 | 설계 간섭 → `design_error` · 선주 코멘트 → `owner_request` · 규정 → `class_rule` · 기자재 사양 → `equipment` · 현장 오작 → `production` | 선주 요청만 계산이 달라짐(늘어난 인도 지연이 허용 지연 — 지체상금 대신 노출 금액) |
| 수행 주체 | 블록 공정의 `Activity.performer`: 직영 = 모두 `direct`, 사내 협력사 = 탑재를 뺀 블록 공정(소조립~PE)을 작업반 하나(`Crew`)가 맡고 탑재는 `direct`, 비면 적지 않음(모름). 사외 제작 협력사(`fabricator_id`)는 두지 않음 | 작업반 몫은 재작업 줄이 따로 나뉨(작업반 단가 cost-v6 = 직영 5만원/시간이라 금액은 같음), 모름도 직영 단가 |
| 결정까지 걸린 일수 | 확정일 = 기준일 + 일수(비면 기준일, 가정) | 확정일 단계로 재작업 배수·발주 단계가 정해짐(결정이 늦어 다음 단계로 넘어간 손실까지) |

**넣을 수 없는 값**은 넣을 수 있는 만큼만 넣고 '변환 메모'로 남긴다.
- 도면 수 > 바뀌는 부재·스풀 수: 도면마다 부재가 하나는 있어야 개정이 생겨 부재·스풀 수까지만.
- 개정 도면 0장: 엔진은 바뀌는 부재가 그려진 도면을 늘 개정해 1장으로.
- 발주 변경 > 재제작 스풀 수, 또는 스풀 없이 발주 변경: 바뀐 부재는 치수 변경이라 발주가 바뀌지 않아 스풀 품목 수까지만
  (남는 건을 다른 연산으로 지어내지 않는다). 재제작 방식이 치수 변경이면 발주 변경을 넣지 않는다.
- 발주 변경이 1건 이상인데 계획상 스풀 발주일이 기준일 뒤면, 그때 이미 발주돼 있었다고 보고 발주일을 기준일로 당긴다.
- 발주 변경 0건이면 스풀 품목 1개를 계획대로 둔다 — 확정일에 '발주' 이상이면 엔진은 발주 변경을 낸다(결과의 '발주 변경(예측/사례)'로 보임).

**기준일(분석 기준일)** = 발견 단계가 진행 중인 구간의 가운데(설정 `schedule.stage_position` 0.5, 내림).
**확정일** = 기준일 + 결정까지 걸린 일수(비면 기준일 — '가정'). 확정일의 블록·발주 단계는 기준일까지의 실적과 계획으로 엔진이 정한다.

| 발견 단계 | 진행 중인 구간 |
|---|---|
| 미착수 | 강재 발주일 ~ 강재 입고 전날 |
| 강재 입고 | 강재 입고일 ~ 소조립 착수 전날 |
| 소조립 ~ 탑재(공정 단계) | 그 공정 착수일 ~ 완료 전날 |

기준일까지 시작·끝난 공정과 들어간 발주 단계는 계획 날짜 그대로 **확인된 실적**으로 둔다(발주는 확인된 진입일 + 기준일 발주대장
관측 하나). 그래서 블록·발주 단계가 '판단 불가'가 되지 않는다.

**공정 계획**: 탑재 착수 계획일(설정 `schedule.erection_start`)에서 공정을 거꾸로 배치한다(생성기 `plan_blocks`와 같은 방식).
기간·간격·발주 리드타임은 생성기 설정 범위의 **가운데 값**이다(난수 없음 — 같은 사례면 같은 지도). 구역 출구 = 탑재 완료 +
`schedule.exit_slack_days`(0 = 이 블록이 구역 출구를 정함), 인도 경계 조건의 여유 = `schedule.float_to_delivery_days`.

## 4. 가정값

양식에 칸이 없어 늘 가정으로 넣는 값과 빈 칸 기본값이다. 백테스트 기본값은 `ripple/eval/backtest/defaults.yaml`(판 `backtest-v2`),
나머지는 생성기 설정(`generator/config.yaml`, 판 `generator-v3`) 범위의 가운데다. 결과의 '고정 가정값' 시트가 실행한 판의 값을
그대로 싣고, 사례별로 기본값을 쓴 칸은 '가정' 시트에 남는다(계산에 쓰이지 않는 빈 칸 — 스풀이 없을 때의 재제작 방식, 실제 지연이
없을 때의 지연 기준 — 은 세지 않는다).

| 항목 | 값(backtest-v2 · generator-v3 · cost-v6) | 출처 |
|---|---|---|
| 바뀐 부재 | 보강재 1개 0.2t, 치수 변경 | 백테스트 기본값 `member.weight_t` |
| 재제작 스풀 1개 | 옛 스풀 0.15t · 4m(새 스풀 무게는 엔진 환산 중량) | `spool.weight_t` · `length_m` |
| 재제작 방식(빈 칸) | 사내 재제작(새 스풀 리드타임 14일). 사외 재발주는 엔진 `lead_time_days.pipe` | `spool.method` · `in_house_lead_days` |
| 지연 기준(빈 칸) | 구역 출구 | `delay_basis` |
| 결정까지 걸린 일수(빈 칸) | 0일(확정일 = 기준일) | 변환 규칙 |
| 블록 무게(빈 칸) | 평 300t · 곡 250t · 선수미 200t · 종류 모름 300t | `block_weight_t` |
| 블록 종류(빈 칸) | 형상 없음 — 난이도 계수 1(평블록과 같음) | 엔진 기본 |
| 블록 난이도 밀도 | 의장품·전장품 수는 양식에 없어 비움 — 밀도 계수 1 | 엔진 기본 |
| 생산 인건비 | 직영 50,000원/시간 · 사내 협력사 작업반 50,000원/시간(cost-v6, 직영과 같음) · 수행 주체 빈 칸도 직영 단가 | 비용 파라미터 `labor_rate_per_hour.prime`·`crew` |
| 사내 협력사 작업반 | 탑재를 뺀 블록 공정(소조립~PE)을 작업반 하나가 맡음, 탑재는 직영 | 변환 규칙(생성기 v3와 같은 나눔) |
| 바뀐 부재 수(부재·스풀 둘 다 빈 칸) | 1 | `member.count` |
| 발주 변경 건수(빈 칸, 스풀 있음) | 스풀 품목 1개(발주 단계는 계획대로) | `spool.po_lines` |
| 개정 도면 수(빈 칸) | 부재 도면 1장 + 스풀 도면 1장(있는 쪽만) | 변환 규칙 |
| 변경 원인(빈 칸) | 미입력 — 선주 요청이 아닌 변경으로 계산(지체상금 계산) | 엔진 기본 |
| 기준일 | 발견 단계 구간의 50% 위치 | `schedule.stage_position` |
| 공정 기간(일) | 소조립 10 + 1.5W/100 · 판넬조립 6.5 + 1.25W/100 · 대조립 15 + 2.5W/100 · 선행의장 8 + 0.75W/100 · 선행도장 5 + 0.75W/100 · PE 4 + 0.75W/100 · 탑재 2.5 + 0.25W/100(반올림, 최소 1) | 생성기 `activities` |
| 공정 사이 간격 | 1일 | 생성기 `gap_days` |
| 발주 | 강재 리드타임 70일 · 스풀 45일 · 소비 공정 착수 전 여유 14일, 자재 확보·제작 착수 = 리드타임 × 0.225 · 0.45 | 생성기 `procurement` |
| 탑재 완료 → 구역 출구 | 0일 | `schedule.exit_slack_days` |
| 구역 출구 → 인도 여유 | 30일(지체상금 경계 조건) | `schedule.float_to_delivery_days` |
| 자재 단가 | 판 900,000원/t · 형강 1,000,000원/t · 스풀 250,000원/m | 생성기 `prices` |
| 선가 | 1,200억원(지체상금에만 쓰임) | 생성기 `ship` |

비용 파라미터(인건비·톤당 공수·재작업 배수·취소율 등)는 엔진 그대로(`params/cost_v1.yaml`)이고 결과의 판에 적힌다.

## 5. 비교와 결과 파일

**예측**(확정일 평가, 엔진 `analyze` 그대로)
- 총변경비용: `AnalysisResult.total`의 대표값·최소·최대(지체상금 포함) — 실제 비용과 견주는 값.
- 지연 파급 비용: `AnalysisResult.delay_ripple`(총액 밖·가정, 엔진 0.10.0). 엔진 값을 그대로 읽어 비용 표의 따로 둔 열('지연 파급',
  '총액 + 지연 파급')에만 싣고 비교에는 쓰지 않는다. 정의는 다시 계산하지 않는다(엔진이 정의를 바꾸면 다시 돌려 값이 바뀐다).
- 공수(MH): 인건비 키가 있는 모든 비용 줄(블록 재작업 — 작업반 몫으로 나뉜 줄 포함 · 도장 뒤 고정 항목 C-04 · 작은 작업 · 도면 개정 ·
  새 부재 제작 등)의 공수 합 — 현장이 말하는 '추가 공수'는 변경 전체 공수라서. 공수는 줄 금액 ÷ 같은 시나리오 인건비로 다시 읽는다
  (금액 = 공수 × 단가인 줄이라 최소·대표·최대가 그대로 나온다). 인건비 키가 여럿인 줄은 엔진이 줄에 적은 대표 공수만 쓴다.
  그중 블록 재작업(R-B01) 공수는 참고 열로 싣는다.
- 지연: 대상 블록 탑재 지연(`added_days_by_activity`) · 구역 출구 지연(`schedule.max_exit_delay_days`) · 늘어난 인도 지연
  (`schedule.delivery.added_delay_days`, 계산하지 못하면 '계산 불가')을 모두 싣는다.
- 지도 점검: 엔진이 낸 발주 변경·도면 개정 수(사례 값과 나란히 — 변환이 뜻대로 됐는지 본다).

**실제와 견주기**
- 실제 대표값 = 최소·최대의 가운데. 비 = 예측 ÷ 실제, 오차 = (예측 − 실제) ÷ 실제(+ = 과대 예측),
  범위 안 = 실제 대표값이 예측 최소~최대 안.
- 공수는 전체 공수와, 지연은 사례의 지연 기준(탑재·구역 출구·인도, 비면 구역 출구)과 같은 예측과 견준다. 지연 차이 = 예측 − 실제(일).
- 실제 값이 비면 '비교 불가'. 실제가 0이면 비·오차를 내지 않고 범위 안만 본다. 지연 기준이 인도인데 인도 지연을 계산하지 못하면
  '비교 불가(인도 지연 계산 불가)'.
- 묶음 요약: 사례 수(계산·계산 불가), 비용·공수마다 비교 사례 수·범위 안 비율·절대 오차 중앙값·오차 중앙값, 지연 차이 중앙값,
  가정으로 채운 칸 수, 판(엔진·계약·전파 규칙·비용 파라미터·생성기 설정·백테스트 기본값).

**결과 파일**(출력 폴더)
- `backtest_result.xlsx`: 요약 · 사례별(사례·비용·공수·지연·지도를 한 행에) · 가정(사례별 빈 칸 채움·변환 메모) · 고정 가정값.
- `backtest_result.md`: 같은 표. 발표 자료·문서로 옮길 때 쓴다.
- 두 파일 모두 원문 칸(변경 내용·블록·구역)이 없고 사례 번호로만 가리킨다. 같은 입력이면 같은 내용이다(검사가 두 번 실행해 본다).

## 6. 한계

- **작은 지도다.** 대상 블록 하나와 그 공정만 있어 이웃 블록·다른 구역·탑재 순서 파급은 사례가 준 범위(부재·스풀·도면·발주 수)만
  반영한다. 실제 조선소 지도를 대신하지 않는다 — 실제 지도에서는 맞대기 이웃·관통·서포트처럼 사례에 적지 않은 연결이 영향을 더한다.
- 구역 출구는 이 블록이 정한다고 본다(여유 0). 실제 구역은 다른 블록이 출구를 정해 지연이 흡수될 수 있어 지연 예측은 큰 쪽이다.
- 바뀐 부재는 모두 같은 무게(0.2t)의 보강재로 본다. 두께·강종 변경처럼 자재가 바뀌는 사례의 자재비·재발주·리드타임은 양식에 값이
  없어 넣지 않는다.
- 인력·정반·크레인 같은 자원 제약은 엔진 한계(`docs/engine.md`(비용·일정) 11절) 그대로다. 지연의 간접비는 엔진의 지연 파급
  비용(가정)으로 따로 보일 뿐 실제 비용과 견주지 않는다.
- 사례 3~5건이라 중앙값·비율은 방향만 본다. 합격 판정은 하지 않는다.

## 7. 실데이터 취급

- 채운 양식과 결과 파일은 **저장소 밖** 로컬 폴더에 둔다. 저장소·외부 문서 도구·외부 AI·발표 자료에 원문을 넣지 않는다.
- 양식에는 회사·호선·사람 이름을 적지 않는다. 사례 번호도 그것을 알 수 없는 번호로.
- 도구는 원문 칸을 읽지 않는다(사례에 담지 않음). 발표 자료·문서로는 `backtest_result.md`를 옮긴다.
- 지도는 실데이터 모드(`DataMode.REAL`)로 만들고 외부 모델을 부르지 않는다.
- 저장소에는 빈 양식을 만드는 코드와 '예시(가상)' 사례만 둔다.

## 8. 엔진이 바뀐 뒤 · 정한 변환

엔진·규칙·파라미터·생성기 설정이 바뀌면 **같은 입력으로 다시 돌리고** 결과의 판 행으로 전후를 견준다.

기준 판(엔진 0.10.0 · 계약 1.32.0 · 생성기 v3 · cost-v6)에서의 대응(검사 묶음 `backtest`가 확인):
- 발견 단계에 PE가 있고 이름은 판넬조립·대조립이다. 드롭다운은 엔진 이름을 따라가고 옛 이름(판계 = 판넬조립, 조립 = 대조립)도 읽는다.
- 블록 종류 → `Block.shape`(재작업 난이도 계수). 의장품·전장품 수는 양식에 없어 비운다(밀도 계수 1).
- 사내 협력사 → 공정의 작업반(`Activity.performer` + `Crew`, 탑재는 직영). 재작업 줄이 작업반 몫으로 나뉘어도 공수·금액 합은 같다.
- 도장 뒤 고정 항목(C-04)은 공수 줄이라 전체 공수에 들어간다.
- 지연 파급 비용은 비교에 더하지 않고 따로 보인다(위 5절).

엔진이 지연 파급 비용 정의를 바꾸면(구역 출구 지연의 여유 반영 등) 같은 입력으로 다시 돌린다 — 백테스트는 필드만 읽는다.

변환 선택(backtest-v2):

| 선택 | 정한 것 | 다른 안(쓰지 않음) |
|---|---|---|
| 스풀 재제작 | 사례마다 양식 '재제작 방식'(사내 재제작 14일 · 사외 재발주 엔진 리드타임 · 치수 변경), 비면 사내 재제작 + 가정 | 한 규칙을 모든 사례에 |
| 기준일·확정일 | 기준일 = 발견 단계 구간 가운데, 확정일 = 기준일 + 결정까지 걸린 일수(비면 0일 + 가정) | 확정일 = 기준일 고정, 단계 첫날 |
| 실제 공수와 견줄 예측 | 공수가 있는 모든 비용 줄의 합(변경 전체 공수) | 블록 재작업만 |
| 실제 지연과 견줄 예측 | 양식 '지연 기준'(탑재 · 구역 출구 · 인도), 비면 구역 출구 + 가정. 결과에는 셋 다 | 한 기준을 모든 사례에 |
| 사내 협력사 인건비 | 작업반 단가(cost-v6 = 직영 5만원/시간과 같음) | 협력사 단가 3만원/시간 |
| 지연 파급 비용 | 실제 비용과 견주지 않고 따로 열(총액 / 총액 + 지연 파급), 비교 기준은 총액 | 총액에 더해 비교 |
| 스풀보다 많은 발주 변경 | 넣지 않고 변환 메모(지어내지 않음) | 부재 교체·의장품 사양 변경으로 채우기 |

## 9. 현직자 실제 사례 1건과 엔진 0.12.0 (2026-10-30)

현직자가 후속 답변으로 준 실제 사례 1건(배관 1개 경로 변경, 선행의장 중 발견, 블록 재작업 없이 배관만 재제작·후행 설치)을 양식
한 행으로 넣어 돌렸다. 입력·결과 파일은 저장소 밖(7절)이고, 여기에는 비율만 적는다. 사례 1건이라 정확도 수치로 쓰지 않는다.

| 판 | 비용 예측 ÷ 실제 | 실제가 예측 범위 안 | 판정 |
|---|---|---|---|
| 엔진 0.11.1 · cost-v7 | 2.66 | 아니오 | 경고(대조립 이후 블록 재작업) |
| 엔진 0.12.0 · cost-v8 | 1.31 | 예 | 검토 필요 |

- 오차의 대부분은 두 곳이었다: 도면 개정 16시간(배관도 1장 개정 실제 3 MH)과, 배관 스풀 재작업에 선체 강재 누적 공수(소조립부터)를
  곱한 것(실제 설치 공수의 약 6배). 엔진 0.12.0은 의장품 재작업을 선행의장 공정부터로(`docs/engine.md`(비용·일정) 4-4), 배관도
  개정 공수를 따로(4-5, `minor_work_hours.drawing_revision_piping`) 두었다.
- 실제 처리(블록은 계획대로 탑재, 배관은 탑재 뒤 설치)는 엔진의 후행 설치 선택지와 같다. 0.11.1은 선행의장이 진행 중인 블록의
  배관을 후행 설치 후보로 보지 않아, 사외 재발주로 가정하면 블록 탑재 지연만 냈다. 0.12.0은 후보로 보고 선택지를 낸다(6-3).
- 공수 비교는 정의가 다르다: 현장 집계는 새 배관 제작(벤딩·도장) 공수를 넣고, 엔진은 새 스풀을 자재(발주 변경·취소 4-2)로 센다.
- 바꾸지 않은 것: 인건비 단가(현장 집계는 설계·생산 한 단가), 스풀 단가·길이 기본값(백테스트 기본값) — 사례가 더 모이면 본다.
